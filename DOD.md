## Honest caveats (non-blocking)

- **(i) Cost variance vs a real model.** Estimate-vs-actual ±15% (§19-6) is only exercised
  meaningfully against a real LLM; the deterministic fake adapter used in offline tests records ≈$0.
  The estimate is surfaced and actuals are metered — validate the ±15% bound during a real-key pilot.
- **(ii) Live scanners at runtime.** Discovery runs in **live** mode when Semgrep/gitleaks/osv-scanner
  are on PATH — they are baked into the worker image (`deploy/docker/Dockerfile.worker`). On a bare
  local host without gitleaks/osv-scanner, discovery falls back to seeded candidates for those (the
  L2→L5 pipeline still runs on real data). **Semgrep/SAST is the one exception (audit finding A4):**
  it is a REQUIRED detector — a missing/erroring Semgrep, or (air-gap) a configured
  `discovery.rulesetsDir` that's absent/empty, now hard-fails the scan (`RequiredDetectorUnavailableError`
  → orchestrator `failScan`) rather than degrading, so an empty scan can never complete and look clean.
  Container/Helm deploys ship Semgrep in the image and are unaffected either way.
- **(iii) Air-gap bundle scope.** `deploy/airgap/{build,import}-bundle.sh` are fully working and
  schema-validated (real SHA-256/size manifests, cosign-or-checksum verification, refuse-by-default on
  an unverified bundle) — but the bundle format only covers deterministic rulesets/advisory data, not
  container images, and of those, only `gitleaks-rules` has real source content in this repo today
  (the OSV/GHSA mirror is a real bulk export but Semgrep rule YAML must still be operator-supplied via
  `--semgrep-rules-dir`). `semgrep-rules` now HAS a runtime consumer (`discovery.rulesetsDir` /
  `MONTR_DISCOVERY_RULESETS_DIR`, audit finding A4); `osv-mirror`/`ghsa-mirror`/`cve-db` do not yet. See
  `deploy/airgap/README.md`.
- **(iv) Statistical power of the 0% FP-rate claim (audit finding A6).** The §19-4 headline —
  precision 100% / FP-rate 0% — is measured from only **TP=11, FP=0** confirmed findings
  (`corpus/baseline.json` `$measurement`). At that sample size, ONE additional false positive on the
  next real corpus run would move the FP-rate from 0% to roughly 8–9% and precision from 100% to
  roughly 91–92% — the claim is honestly measured but not yet statistically meaningful. Recall
  (25.0%, 11/44) is published alongside it for exactly this reason: it is the number that keeps a
  near-perfect FP-rate from reading as "the scanner is accurate" when the truer statement is "the
  scanner confirms very little, and what it does confirm has not yet been wrong." The gate itself
  already reflects this: `packages/qa/src/report.ts`'s `sampleSizeCaveat` prints this exact warning
  in every `qa:corpus` run while TP+FP stays under 30 (the rule-of-thumb floor for a proportion
  estimate to be meaningful), and `recallMin`/`precisionMin`/`fpRateMax` are all three enforced with
  equal weight (`packages/qa/src/baseline.ts` `evaluateBaseline`) so a regression in any one of them
  — not just FP-rate — blocks CI. The fix for the underlying gap is corpus growth (see
  `corpus/README.md` "A17: corpus growth"), not a looser bar.
