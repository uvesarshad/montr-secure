# Database Architecture and Models

Scope: Relational database schema, Prisma ORM models, multitenancy design, field encryption, and hash-chain audit storage.
Rendering context: Server
Project tier: 4
Last updated: auto

Overview
Montr Secure persists data in PostgreSQL using the Prisma ORM managed in packages/state-store. The database implements strict row-scoped multitenancy, where all entities carry a client identifier and queries are explicitly scoped in repository layer wrappers. Sensitive fields are encrypted at rest using AES-256-GCM, and security audit events are stored in an append-only, cryptographic hash-chained table.

Multitenancy and Tenant Isolation
Row-Scoped Isolation: Every database model contains a clientId foreign key indexed for rapid tenant filtering. All query operations in packages/state-store/src/prisma-store.ts automatically enforce clientId scoping to prevent cross-tenant data leakage.
Single-Tenant and Air-Gap Mode: For high-isolation deployments, dedicated Postgres database schemas or isolated database instances can be provisioned per client without schema modifications.

Field-Level Encryption at Rest
Encrypted Columns: High-sensitivity columns including LlmCredential apiKey and refreshToken, as well as RedTeamScenario steps, are annotated with encryption directives and transformed via AES-256-GCM before writing to Postgres.
Key Resolution: Encryption keys are supplied via environment variables, Kubernetes secret mounts, or HashiCorp Vault KV v2 lookups resolved at server startup.

Core Relational Models in packages/state-store/prisma/schema.prisma
Client: Represents a tenant organization owning users, scans, application maps, audit logs, DAST targets, and credentials.
User: Represents an authenticated operator, approver, or viewer carrying an Argon2 password hash and role designation.
LlmCredential: BYO-key configuration storing encrypted provider credentials, provider type, and verified key tier. `provider` is the `Provider` enum — additively extended by migration `11_llm_provider_expansion` (A3) from the original four (anthropic, bedrock, vertex, azure) to ten, adding openai, google, xai, moonshot, zhipu, deepseek — the six BYO-key providers reached through the generic `OpenAiCompatibleAdapter` (packages/llm-gateway/src/adapters/openai-compatible.ts). STRICTLY ADDITIVE (`ALTER TYPE ... ADD VALUE`, mirroring migrations 7/8's enum-extension precedent) — no existing row or enum value is affected.
AppMap: Structural snapshot of a repository commit containing routes, entry points, data stores, ORM models, taint flow graphs, and (B1) an optional persisted ThreatModel.
Route, TaintSource, TaintSink: Structural application elements linked to AppMap representing HTTP paths, input sources, and database/command sinks.
Scan: Primary execution entity recording repository target, branch, scan mode, status, gate state, cost estimates, and actual costs.
ScanState: Checkpoint entity recording active layer, completed layer history, and resume tokens enabling pipeline pause and resume.
CandidateFinding: Raw, unverified issues captured during Layer 1 discovery, linked to source tools (Semgrep, gitleaks, OSV).
ProbableFinding: Correlated findings generated in Layer 2 with reachability, exposure, and impact scores, linked to root causes.
ConfirmedFinding: Exploit-verified vulnerabilities generated in Layer 3 with attached static or live ProofArtifact JSON.
Fix: Remediation entity generated in Layer 4 containing unified diff patches, proof-of-fix tests, and auto-eligible or human-required risk classifications.
PullRequest: Version control tracking record storing PR URLs, branches, status, and associated fix IDs.
Report: Monolithic document entity storing the finalized Layer 5 security report and compliance mappings.
DastTarget: Allowlisted staging URLs with approved rate limits and concurrency contracts.
AuditEvent: Immutable, append-only log record storing sequential actions, actor metadata, previous hash, and SHA-256 hash chaining.
CustomRule, RedTeamScenario, ScanSchedule, PostureSnapshot: Scale and intelligence entities managing custom detection rules, attack playbooks, cron schedules, and historical trend snapshots. RedTeamScenario additionally carries four written live-run authorization columns — see the Written Live-Run Authorization section below.
LearnedFact: Durable, per-client, per-repo cross-scan memory record (custom sanitizer name, framework idiom, operator decision, or a system-recorded confirmed exploit shape) with free-form structured content and provenance, injected as additive context into a later scan's Layer 1, 2, and 3 LLM prompts — confirmed_exploit_shape and custom_sanitizer rows are ALSO consumed structurally, not just as prompt text (see the Cross-Scan Memory section below).
CodeChunk: AST-chunked source (one function, method, or class) plus its embedding vector, scoped to a client/repo/commit and linked to the AppMap it was built alongside (E5, semantic codebase index).
DetectionRule, AttackPath, DetectionCoverage: Blue-team / purple-team entities (B1) — a generated detection rule for a confirmed finding, a chained kill-chain across confirmed findings, and a telemetry-coverage verdict for a confirmed finding, respectively.
DetectionRulePushTarget: Suggested-enhancement entity (2026-09-12 red/blue agentic-posture audit) — one client's configured real push destination (Splunk HTTP Event Collector today) for generated detection rules, with an AES-256-GCM field-encrypted token. See the "Detection-Rule Push Target (encrypted)" section below.

Cross-Scan Memory (§15, E8)
LearnedFact rows are scoped by clientId and repo and carry a LearnedFactType (custom_sanitizer, framework_idiom, operator_decision, or confirmed_exploit_shape — added migration 14_learned_fact_confirmed_exploit_shape), a free-form Json content field, and a Json provenance field recording the source (operator or scan_derived), the recording scan or operator id, and a timestamp. custom_sanitizer/framework_idiom/operator_decision rows are written through POST /api/v1/learned-facts (an operator-facing route, apps/api/src/routes/learned-facts.ts); confirmed_exploit_shape rows are SYSTEM-recorded only, written exclusively by apps/worker/src/runners.ts's recordConfirmedExploitShapes for a finding Layer 3 genuinely confirmed on real proof — deliberately excluded from POST /api/v1/learned-facts' operator-writable enum (apps/api/src/schemas.ts's RecordLearnedFactBodySchema) so an unverified claim can never masquerade as real confirmed-exploit history. confirmed_false_positive is deliberately NOT a LearnedFactType member and is never persisted on this table: that fact class already lives in the audit log's finding.marked_false_positive events (A10's FalsePositiveMarkRepository) and is merged in at read time by apps/worker/src/runners.ts's loadLearnedFactsContext, so the same mutation never has two authoritative homes. packages/state-store/src/learned-facts.ts's LearnedFactRepositoryImpl provides record and listByRepo (newest first, capped), both scoped by clientId per this schema's row-scoping discipline. See docs/modules/confirmation.md's "Confirmed-Exploit-Shape Priors and Learned Sanitizer Conventions" entry for how confirmed_exploit_shape and custom_sanitizer rows are consumed by Layer 2/3 (E8 extension, 2026-09-12).

Semantic Codebase Index (E5)
CodeChunk rows are written and read exclusively through packages/state-store/src/code-chunk.ts's PrismaCodeChunkRepository, deliberately kept OUT of the main StateStore aggregate (see that file's doc comment) since its only consumer today is packages/semantic-index, not a wired pipeline layer — construct it directly via createCodeChunkRepository(prisma). Columns: repo/commitSha/file/startLine/endLine locate the chunk in source; language and kind (function, method, or class) and an optional symbolName describe it; contentHash (sha256 of content) lets a rebuild skip re-embedding an unchanged chunk; embeddingModel records which model produced the vector. embedding is declared Unsupported("vector(1536)") in schema.prisma — Prisma Client generates no typed accessor for a pgvector column, so every read/write goes through $queryRaw/$executeRaw rather than the generated delegate; the 1536 width is fixed to the one embedding model packages/llm-gateway/src/embeddings.ts implements today (Azure OpenAI text-embedding-3-small). ⛔ This table REQUIRES the Postgres pgvector extension, which the bundled deploy/docker/docker-compose.yml postgres:16-alpine image and deploy/helm/montr-secure's default postgres.image do NOT currently include — migration 5_semantic_code_index's CREATE EXTENSION IF NOT EXISTS vector fails prisma migrate deploy outright on either bundled image until it is swapped for one that ships pgvector (e.g. pgvector/pgvector:pg16); this is documented as a required follow-up, not applied to deploy/ in this change. See docs/modules/semantic-index.md for the chunker/embedder/query-path that populates and reads this table.

Threat Model Persistence (B1)
`AppMap.threatModel` is a nullable Json column holding the `ThreatModel` shape (@montr/contracts, defined in `threat-model.ts` — trust boundaries, attack surface, abuse cases, scope hints; landed today via E6). Before B1 this value existed only on the in-memory `AppMap` Zod object built by packages/appmap/src/build.ts and was silently dropped the moment an AppMap was persisted — the Prisma `AppMap` model had no column for it and `packages/state-store/src/mappers.ts`'s `appMapScalarsToCreate`/`appMapFromRows` never referenced it. B1 closes that gap by adding the column directly to `AppMap` rather than a separate table: a threat model is 1:1 with the AppMap it was derived from, has no independent lifecycle (it is never updated, listed, or queried on its own), and B7 (report) / B10 (compliance export) both need it alongside the rest of the AppMap they're already loading — a join would buy nothing. Older rows and any AppMap built before E6 have `threatModel: null`.

Blue-Team / Purple-Team Entities (B1)
Three new models extend the pipeline past exploit confirmation into detection engineering, all row-scoped by `clientId` (real `Client` + `Scan` foreign keys, `onDelete: Cascade` from `Scan` — mirrors `ConfirmedFinding`'s precedent) with `findingId`/`detectionRuleId` kept as PLAIN string references rather than Prisma relations, mirroring `ConfirmedFinding.probableId`'s existing loose-reference precedent across finding tiers (and unavoidable for `AttackPath.steps`, where finding ids live inside a Json array).

- `DetectionRule`: one generated detection rule (Sigma YAML, an OTel query, or a SIEM query — `format` is a plain String column, not a Prisma enum, so B3 can add more formats without a migration, mirroring `RedTeamScenario.category`) for one `ConfirmedFinding`. `mitreTechniques` is a Json `string[]` of ATT&CK technique ids (B2's `mitreTechniqueIdsForCategory`, packages/contracts/src/mitre.ts, is B3's default source for these — see below). `provenance` reuses the existing `ProofType` enum ("static" | "live") to record whether the rule was derived from a static data-flow path or a live-DAST transcript, mirroring `ConfirmedFinding.proofType`. `logSignature` (B3/B4, migration `10_detection_rule_log_signature`) is a nullable Json `DetectionLogSignature | null` column — `{ fields: string[], pattern: string, falseAlarmSources: string[] }` (packages/contracts/src/blue-team.ts) — the human-readable "what this looks like in your logs" narrative attached to the same row as the generated rule `content`; `null`/absent for any pre-B4 row. B3's generation logic itself (packages/report/src/detection-rules) is read-only against this table's shape — see docs/modules/reporting-vcs.md.
- `AttackPath`: a chained kill-chain across >= 2 confirmed findings (e.g. "public route -> SSRF -> metadata endpoint -> credentials"). `steps` is a Json ordered array of `{ findingId, note? }` (a small, read-mostly, always-whole-object structure, never queried hop-by-hop — mirrors `taintFlows`/`ScanState.completedLayers`'s ordered-array-as-Json precedent) rather than a join table. `feasibilityScore` (0..1) and `severity` (the `Severity` enum) score the end-to-end path; `narrative` is the human-readable summary. A later wave builds the graph algorithm that produces these rows.
- `DetectionCoverage`: whether a target's existing telemetry would catch a confirmed finding if exploited. `detected` is a genuine three-value `DetectionStatus` Prisma enum (`detected` | `not_detected` | `unknown`) rather than a nullable Boolean, so "we don't have enough telemetry-surface info to say" is a real, queryable third state rather than an absent column. `detectionRuleId` optionally names the `DetectionRule` covering the finding. `verification` is a nullable Json `DetectionVerificationResult | null`, absent until B5's purple-team loop actually runs a scenario against the target and records whether the expected detection fired.

Encryption: none of `DetectionRule.content`, `AttackPath.narrative`, or `DetectionCoverage.reasoning` are field-encrypted, despite describing exploit-adjacent detail. Two existing precedents justify this: (1) `CustomRule.body` — itself a detection-rule body — is explicitly documented as not encrypted ("needs validation" instead); (2) `ConfirmedFinding.proofArtifact`, the single most sensitive exploit-detail field in this schema (a live HTTP request/response transcript against a real target for `kind: "live"` proofs), is already stored as plain Json. A `DetectionRule` is generated FROM an already-unencrypted `ConfirmedFinding`/`proofArtifact` — encrypting the derived detection rule while its source proof sits in plaintext next to it would add no real confidentiality (DB access already exposes everything the rule was built from) while complicating the query/index patterns B7 and B10 need. This mirrors `RedTeamScenario.steps`'s DIFFERENT choice (encrypted) precisely because that field is a runnable attack playbook bound to a live target, not a detection artifact describing one.

Detection-Rule Push Target (encrypted) (suggested enhancement, 2026-09-12 red/blue agentic-posture audit, migration `13_detection_rule_push_target`)
New model `DetectionRulePushTarget` closes the "detection rules are only ever downloaded, never pushed anywhere" gap flagged in this audit's suggested-enhancements section. One row per client (`clientId @unique`, mirroring `LlmCredential`'s exact 1:1-per-client shape, including a `Client.detectionRulePushTarget?` back-relation) holding the operator-configured destination: `type` (a plain String defaulting to `"splunk_hec"`, mirroring `DetectionRule.format`'s precedent so a real Elastic/Sentinel adapter needs no migration once implemented — see `packages/report/src/detection-rules/push/types.ts`), `endpointUrl`, optional `index`/`sourcetype`, and `hecToken` — `/// @encrypted` AES-256-GCM at rest, the identical envelope/AAD (`clientId`) scheme `LlmCredential.apiKey` already uses (`packages/state-store/src/crypto.ts`'s `FieldCipher`). `packages/state-store/src/detection-rule-push-target.ts`'s `DetectionRulePushTargetRepositoryImpl` is a deliberate mirror of `CredentialRepositoryImpl` (repositories.ts): `upsert`/`get` (decrypted)/`getMetadata` (never the secret)/`delete`, same `requireCipher` fail-fast. Configured via `POST`/`GET`/`DELETE /api/v1/detection-rules/push-targets` (approver-only to write — see docs/auth/authorization.md) and consumed by `POST /api/v1/detection-rules/push{,-bundle}`, which route the decrypted credential through `packages/report/src/detection-rules/push`'s Splunk HEC adapter — see docs/modules/reporting-vcs.md for the full push design and docs/api/route-handlers.md for the routes. Not field-encrypted: `type`/`endpointUrl`/`index`/`sourcetype` (non-secret configuration, same distinction `LlmCredential.provider`/`endpoint` already draw against `apiKey`).
(This migration and `confirmed_exploit_shape`'s below both landed the same day from two concurrent agents and briefly collided on the numeral `13` — resolved by the coordinator by renumbering `confirmed_exploit_shape`'s migration to `14_learned_fact_confirmed_exploit_shape`, restoring the sequentially-numbered directory convention.)

Written Live-Run Authorization on RedTeamScenario (A1, 2026-09-12, migration 12_scenario_live_authorization)
RedTeamScenario gained four additive, nullable columns so real worker-side scenario execution (apps/worker/src/scenario-runs) can be gated behind an explicit, auditable written authorization beyond RBAC and the allowlist. liveAuthorizedById is a foreign key to the approver User who granted it (mirrors DastTarget.approvedById's existing relation pattern, a distinct relation name so one User can carry both). liveAuthorizationReference is a required-at-the-application-layer free-text record — a ticket number or signed agreement reference — that DastTarget's own approve flow never captured. liveAuthorizedAt is the grant timestamp. liveAuthorizedForVersion binds the grant to the scenario's exact version at authorization time: apps/api/src/routes/scenarios.ts's edit route clears all four columns on every update (rather than merely bumping version out of sync with them), so a stale authorization can never silently cover a changed scenario. packages/contracts/src/phase4.ts's hasLiveRunAuthorization is the single shared predicate every layer (the API route, the worker consumer, and the console's status badge) evaluates against these four columns, so none of the three can drift from what the others enforce. STRICTLY ADDITIVE — no existing column, table, or enum value was removed, renamed, or made non-nullable.

Audit Log Scrub Gate
`PrismaAuditLogClient.append` in packages/state-store/src/audit.ts is the single write chokepoint for every AuditEvent, reached by all callers across apps/api and apps/worker. It unconditionally runs both free-form text fields — `metadata` and `summary` — through @montr/security's content-aware `redactSensitive` before hashing/persisting, then re-verifies the redacted output with that package's independent `findLogViolations` verifier as defense in depth. This promotes @montr/security's scrubber (previously exercised only by tests certifying @montr/telemetry's separate hot-path log scrubber) into a real runtime gate on the persistence path itself, closing the gap where AuditEventInput.metadata's Zod type (`z.record(z.string(), z.unknown())`) could not enforce "MUST be scrubbed" beyond a code comment. The gate is fail-safe rather than fail-closed: on the residual case where content still trips the verifier after redaction, the event is still persisted with an anomaly-marker payload rather than being rejected, so a safety-relevant write (e.g. a kill-switch event) is never silently lost.

Migration Strategy
Schema Migrations: Schema modifications are authored in packages/state-store/prisma/schema.prisma and validated using pnpm prisma:validate and pnpm prisma:format.
Generation: Client code generation is triggered via pnpm prisma:generate during root postinstall hooks.
Latest migration: 12_scenario_live_authorization (A1, 2026-09-12) adds RedTeamScenario's four written live-run authorization columns described above — additive only, following the same zero-padded, sequentially-numbered directory convention as migration 11_llm_provider_expansion before it.

Migration Directory Rename (A8, 2026-09-09) — one-time operator action for existing databases
What happened: Prisma applies migrations in lexicographic directory order. The original single-digit directory names (`0_init` ... `9_blue_team_entities`) sorted after `10_detection_rule_log_signature` and `11_llm_provider_expansion`, so a fresh database died applying migration 10 before a table three migrations later actually created it — no fresh install could migrate at all (docs/plan/26-09-09-audit-july-line-divergence.md A8). The fix zero-padded the ten single-digit directories to `00_init` ... `09_blue_team_entities`; `10_` and `11_` were already two digits and are unchanged.
Who is affected: any database that already ran `prisma migrate deploy` against the OLD directory names before this fix — i.e. any pre-existing dev machine, staging environment, or production database. Prisma records applied migrations by directory name in the `_prisma_migrations` table, so those databases now see the ten renamed migrations as brand new and will try to re-run them on the next deploy (fails outright, or worse, partially re-applies DDL against tables that already exist). **Do this before deploying past this commit against any database with data worth keeping.**
What a fresh install needs: nothing. `_prisma_migrations` starts empty, so `prisma migrate deploy` (the compose `migrate` service) applies all twelve migrations under their current (padded) names on its own, in the correct order.
How to fix an affected database: run `scripts/resolve-migration-rename.mjs`. It connects to the target database, inspects `_prisma_migrations` directly, and classifies it into fresh (nothing to do), old names present (needs resolving), or already correct (nothing to do) before doing anything — it never assumes which case applies. It refuses outright, printing exactly what it found, if `_prisma_migrations` contains anything unexpected (an unfinished/failed migration row, or a migration name it doesn't recognize). Defaults to a dry run; pass `--apply` to actually act. Idempotent — safe to re-run, including after a partial `--apply` run.

```bash
# Dry run against deploy/docker/.env's DATABASE_URL (default) — prints what it would do.
node scripts/resolve-migration-rename.mjs

# Point at a specific database explicitly instead:
node scripts/resolve-migration-rename.mjs --database-url=postgresql://user:pass@host:5432/db

# Actually resolve the renamed migrations (once satisfied with the dry run):
node scripts/resolve-migration-rename.mjs --apply
```

Under the hood, for each of the ten renamed migrations still recorded only under its old name, `--apply` runs `pnpm --filter @montr/state-store exec prisma migrate resolve --applied <new_name>` — Prisma's own supported way to mark a migration applied without re-running its SQL — then re-queries `_prisma_migrations` to verify the fix actually took, rather than trusting the CLI's exit code alone. Exit codes: `0` nothing to do or apply succeeded, `1` refused (unexpected state) or apply failed partway, `2` dry run found renamed migrations still needing `--apply`. See the script's own header comment for full detail; verified locally against a real `pgvector/pgvector:pg16` container across all three states (fresh, old-names, already-correct) plus the anomaly-refusal paths.
