## Suggested enhancements

- [ ] **(E1)** Build an agentic investigation loop in Layer 3 — the highest-leverage single change. Give confirmation a tool-using agent with read-only repo tools (`read_file`, `grep`, `find_definition`, `query_call_graph`, `list_routes`, `get_orm_model`) so it investigates a finding across files instead of receiving pre-chewed metadata. Run with adaptive thinking and a task budget. This is what lifts IDOR and broken access control off 0%. Depends on A18 and E10.
- [ ] **(E2)** Let the LLM propose findings, gated by executable proof. Add a discovery pass that may propose candidates the deterministic tools missed, but require a failing test or live probe transcript before anything reaches `confirmed`; unproven proposals go to the appendix. Autonomy earned by proof, not granted by trust.
- [ ] **(E3)** Replace the fixed DAST payload `switch` with an adaptive exploit agent that sends a probe, reads the response, reasons, and adapts. Keep every existing guard unchanged — allowlist, production block, kill switch, rate limits, blast-radius caps — as the sandbox it runs inside.
- [ ] **(E4)** Add multi-agent adversarial confirmation: N independent verifiers with distinct lenses (exploitability, reachability, business impact, "try to refute this"), majority vote. Attacks the precision/recall tradeoff directly and yields a confidence score for E9.
- [ ] **(E5)** Build a semantic codebase index (pgvector or on-prem equivalent) over AST-chunked code, built once per commit alongside the App Map and reused by diff scans. Gives cross-file context without blowing the token budget and turns one confirmed finding into a swept class of findings.
- [ ] **(E6)** Add a threat-model agent at Layer 0.5 that derives trust boundaries, attack surface and abuse cases from the App Map, then uses them to **drive which rules and probes run** — the shift from "run every rule and filter" to "hunt this app's actual risks".
- [ ] **(E7)** Ship the blue-team half to make the product genuinely purple. Umbrella item — decomposed into the **Blue team build** section below; complete when B1–B12 land.
- [ ] **(E8)** Add cross-scan memory: persist per-repo learned facts (custom sanitizer names, framework idioms, confirmed false positives, operator decisions) and inject them into later scans' prompts. Genuinely closes the PRD §15 loop that A10 shows is dead code.
- [ ] **(E9)** Implement dynamic model-tier escalation — cheap model first, escalate on low confidence or verifier disagreement. The `triage`/`default`/`confirmation` tier machinery exists and nothing uses it adaptively.
- [ ] **(E10)** Modernize the LLM gateway, which unblocks most of the above: tool use / function calling, real structured outputs with JSON schema, prompt caching on the stable system+AppMap prefix, adaptive thinking with an `effort` setting for confirmation, streaming wired through to the console, real token counting, and model fallback.
- [ ] **(E11)** Build an AI-application security ruleset that scans _target_ apps for prompt injection, unsafe tool/function exposure, unescaped LLM output rendered to users, secrets leaking into prompts, and missing output validation. Add a `prompt_injection` category to the taxonomy.
- [ ] **(E12)** Build the autonomy surface: `montr scan .` CLI, a GitHub App running diff-mode per PR with review annotations, and scheduled continuous scanning with delta-only reporting.
- [ ] **(E13)** Implement real proof-of-fix in an ephemeral container — stand the app up, replay the confirmed exploit, assert it now fails, attach the transcript. Also provides E2's evidence mechanism and E3's oracle.
- [ ] **(E14)** Build an external benchmark harness scoring against OWASP Benchmark and Juliet, plus a published head-to-head against raw Semgrep and CodeQL on the same corpus, per release.
- [ ] **(E15)** Wire eval-driven prompt optimization: connect the dead prompt registry to the corpus scorer so prompt versions are automatically A/B'd against ground truth with per-version regression gating.
- [ ] **(E16)** Broaden target coverage in priority order: IaC/Dockerfile/Kubernetes/Terraform, SBOM (CycloneDX), supply-chain risk (typosquatting, install scripts, malicious packages), OpenAPI/API-spec review, container image scanning, then cloud posture.

## Blue team build

New scope. The blue-team half was never specified: the PRD names "blue-team hardening" exactly once, in the thesis sentence at line 26, and never again — it appears in no layer of §7 Agent Topology, no entity in the §9 data model, no section of the §12 report spec, and no item in the §19 Definition of Done. The build followed §7 faithfully, and §7 is entirely red and static. These tasks add the missing half. `packages/state-store/src/redteam-catalogue.ts` (`REDTEAM_SCENARIO_CATALOGUE`, `instantiateScenario`, OWASP coverage mapping) and the gated execution engine in `packages/confirm/src/scenarios.ts` are real, working assets to build the purple loop on.

- [ ] **(B1)** Extend the contracts spine with the blue-team entities: `DetectionRule`, `ThreatModel`, `AttackPath`, and `DetectionCoverage`. Follow the existing frozen-spine discipline in `packages/contracts` and add the matching Prisma models plus migrations (`docs/api/database.md` must be updated per the project hard rules).
- [ ] **(B2)** Add MITRE ATT&CK mapping (tactic + technique IDs) per finding category, alongside the existing OWASP/CWE mapping. Reuse the exhaustive `Record<Category, readonly string[]>` pattern from `packages/report/src/exports/controls.ts` so the compiler enforces completeness, and surface the IDs in the report and in SARIF `properties.tags`.
- [ ] **(B3)** Generate detection rules per confirmed finding — Sigma as the primary format, plus OTel/SIEM query variants. Derive them from the confirmed proof: the live DAST transcript where one exists, otherwise the static data-flow path and the route's request shape.
- [ ] **(B4)** Add a "what this looks like in your logs" section per confirmed finding: the concrete log signature, the fields to alert on, and the expected false-alarm sources. This is the single most useful blue-team output for an AppSec buyer and is cheap once B3 exists.
- [ ] **(B5)** Build the purple-team verification loop — the core differentiator. Run a red-team scenario through the existing gated engine (`packages/confirm/src/scenarios.ts`), then verify whether the B3-generated detection rule actually fires against the resulting telemetry. Report detected / undetected per scenario. This is what makes the product genuinely purple rather than red-with-a-report.
- [ ] **(B6)** Implement detection coverage gap analysis: for each confirmed finding, determine whether the target's existing telemetry would catch it. Requires ingesting the target's logging/monitoring configuration during Layer 0 — extend the App Map with a `telemetry_surfaces` field.
- [ ] **(B7)** Generate a threat model artifact at Layer 0.5: trust boundaries, STRIDE per element, and abuse cases derived from the App Map. Distinct from E6, which uses the same analysis to drive scan scope — this task produces the reviewable deliverable.
- [ ] **(B8)** Build an attack-path graph across confirmed findings, chaining them into realistic kill chains (e.g. public route → SSRF → metadata endpoint → credentials). Rank paths by end-to-end feasibility rather than scoring findings in isolation.
- [ ] **(B9)** Generate hardening recommendations distinct from code fixes: security headers, CSP, cookie policy, rate limits, WAF rules, network policy, and framework configuration. These are blue-team config outputs, not patches, and must not flow through the Layer 4 auto-fix risk classifier.
- [ ] **(B10)** Add a blue-team section to the report and extend the compliance exports so detection coverage counts as SOC 2 / ISO 27001 evidence. Reuse the existing control-catalog and evidence-record machinery in `packages/report/src/exports/`.
- [ ] **(B11)** Build the console UI for the blue team: a detection-rules page with export, an ATT&CK coverage matrix/heat map, the attack-path graph view, and purple-loop results (which scenarios were detected).
- [ ] **(B12)** Build a blue-team golden corpus with labelled detection ground truth — which scenarios should fire which rules — and add a CI regression gate for detection precision/recall, mirroring the existing `corpus/baseline.json` gate so the blue side is measured as rigorously as the red side.
