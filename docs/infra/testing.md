# Testing Strategy and Quality Assurance

Scope: Test automation strategy, frameworks, directory coverage, golden corpus scoring, and CI execution.
Rendering context: Server
Project tier: 4
Last updated: auto

Overview
Montr Secure implements a comprehensive, multi-tiered testing framework encompassing over six hundred unit, integration, invariant, and end-to-end test suites. All tests execute completely offline without outbound network calls, utilizing deterministic mock fixtures and fake LLM adapters. Automated quality gates enforce code coverage baselines, architecture boundary rules, stack-agnostic invariants, and statistical precision and recall thresholds measured against a curated golden vulnerability corpus.

Test Types and Scopes
Unit Tests: Located across packages/_/src/\**/_.test.ts and apps/_/src/\**/_.test.ts, testing isolated functions, Zod schema validation, state machines, and algorithmic units using Vitest.
Integration Tests: Located in tests/ and apps/worker/src/**/*.test.ts, testing multi-package interactions, Fastify API endpoints, Prisma database repositories, and BullMQ queue orchestration.
Invariant Tests: Located in tests/stack-agnostic.invariant.test.ts, tests/security.invariants.test.ts, and tests/package-boundaries.test.ts, verifying that Layer 2 correlation and Layer 4 fix generation remain independent of specific language ASTs, that egress guard rules hold, and that internal monorepo package boundary rules are strictly maintained.
End-to-End Scans: Executed via scripts/e2e-scan.mjs and apps/worker/src/e2e-scan.test.ts, running full six-layer pipeline workflows against realistic repository fixtures to generate verified reports and fix pull requests.
Golden Corpus Evaluation: Managed by packages/qa and executed via scripts/corpus-scan.mjs, running scans against sixteen curated vulnerable and clean repositories in corpus/ (44 labelled exploitable findings) across TypeScript, Python, and JVM stacks to calculate precision, recall, and false positive rates. The clean-negative repos (validator.js, gson, requests) are vendored in full; several vulnerable teaching-app repos (dvna, pygoat, javaseccode, spring-petclinic) are trimmed excerpts of larger upstream projects, not the whole application — see corpus/README.md's Layout table and provenance table for the exact per-repo file counts and scope (audit finding A28). The CI gate (packages/qa/src/baseline.ts evaluateBaseline, thresholds in corpus/baseline.json) enforces recallMin with the same weight as fpRateMax/precisionMin — a recall regression fails the build exactly like a precision/FP-rate regression, not just an informational number (AGENT NOTE: never report FP-rate/precision without recall alongside it — packages/qa/src/report.ts is the single place both are rendered together, in text (formatCorpusScore) and JSON (toJsonReport)). At the current real measurement (TP=11, FP=0, precision 100%, recall 25.0%), the 0% FP-rate is honestly measured but not yet statistically meaningful at that sample size; formatCorpusScore's sampleSizeCaveat prints this caveat automatically in every qa:corpus run while confirmed findings (TP+FP) stay below 30, and the same caveat is stated in DOD.md item 4 and corpus/baseline.json's $statisticalCaveat.
Model-Variance Harness (A23): packages/qa/src/model-variance.ts's runModelVariance scores the corpus once per model and emits a ModelMatrix (formatModelMatrix), flagging an accuracyCliff when a below-floor model's recall falls materially short of the best floor-or-better model. Its default scanner (qa:variance, no flags — packages/qa/src/real-confirmation-scanner.ts's realConfirmedForRepo) runs the REAL @montr/confirm static-confirmation engine, once per model in packages/fixtures' listModels() (RECOMMENDED_MODEL_MATRIX's triage/default/confirmation tiers), against the two @montr/fixtures sample repos ("vulnerable-nextjs", "clean-nextjs" — the only repos with a hand-built, schema-valid AppMap + ProbableFinding[] fixture today) — never the full 16-repo golden corpus, which corpus/baseline.json's minReposScored:14 assumes and this harness does not attempt to cover (widening REAL_SCANNER_FIXTURES is future work). Per-model differentiation comes from gatewayForModel: a fake gateway whose CONFIRMATION-purpose canned response depends on the model's own belowFloor flag (confirms if floor-or-better, vetoes — golden rule #4's fail-safe demotion — if below floor), the same createFakeLlmGateway({ cannedByPurpose }) convention tests/confirm.static.test.ts's own veto test already uses, just picked per model instead of one fixed response for every caller. This is what makes a genuine accuracy cliff show up as a real, differing recall per row instead of the pre-A23 bug (perfectConfirmedForRepo ignored the model parameter entirely, so every row scored an identical, tautological 100%) — pass --variance-selfcheck to opt back into that old tautological self-check as a plumbing-only smoke test (mirrors qa:corpus vs qa:corpus:selfcheck). Scored against REAL_VARIANCE_BASELINE (recallMin 0.5, minReposScored 2 — sized for this harness's narrower scope, not corpus/baseline.json), gating on floor-or-better rows only; a below-floor cliff is informational (printed in the matrix, never blocking). Wired into CI as a step in the golden-corpus job (.github/workflows/ci.yml), fully offline (fake gateway, no live provider credentials or spend).
Eval-Driven Prompt Optimization (E15): packages/qa/src/prompt-eval.ts connects the versioned prompt registry (docs/modules/llm-gateway.md's Versioned Prompt Registry section — packages/llm-gateway's resolvePromptVersionTemplate/InMemoryPromptVersionRegistry, E15) to the golden-corpus scorer, so a candidate prompt VERSION for a real call site (e.g. confirm.static_review.system, Layer 3) can be A/B'd against the currently-active version before promotion. evaluatePromptCandidate(opts) registers both templates in an isolated InMemoryPromptVersionRegistry, runs the REAL @montr/confirm engine (via real-confirmation-scanner.ts's confirmedForRepoWithGateway, the same A23 pattern) once per version — marking a different row active between runs — scores each with the SAME scorer corpus/baseline.json's CI gate uses (scoreScanResults), and applies a regression gate (evaluateBaseline) that defaults to a RELATIVE floor built from the active version's own measured score: a candidate that scores worse (lower recall, higher FP-rate, lower precision) is rejected, mirroring corpus/baseline.json's shape as a live A/B comparison instead of a fixed committed file. Because @montr/fixtures' fake LLM adapter returns a fixed canned response per call purpose (it cannot "read" a prompt the way a real model would), PromptEvalGateway makes the outcome genuinely prompt-content-sensitive by judging the RESOLVED system-prompt text against DEFAULT_PROMPT_RUBRIC — keyword markers ("exploitab", "conservativ", "uncertain") drawn directly from the REAL confirm.static_review.system fallback string, so today's production prompt passes by construction and a genuinely vaguer candidate fails — the same createFakeLlmGateway({cannedByPurpose}) convention A23's gatewayForModel uses, generalized from "vary by model tier" to "vary by prompt version." Scoped, like A23, to the two @montr/fixtures sample repos with a hand-built AppMap fixture (a caller supplies LoadedCorpus explicitly — no filesystem I/O inside prompt-eval.ts itself, mirroring runModelVariance's ModelVarianceOptions.corpus). Real tests (packages/qa/src/prompt-eval.test.ts) prove the core claim: an identical candidate is promoted, a rubric-failing candidate scores materially lower recall and is rejected, a richer/superset candidate is promoted, and evaluation is deterministic. Not wired into CI as an automated gate in this change (a real operational promotion workflow — who authors a candidate, when the eval runs, how "promote" flips the real DB's isActive flag — is a follow-up decision); the CORE mechanism (versioned registry + eval-and-compare harness + regression gate) is built and tested. packages/qa gained a new @montr/llm-gateway dependency for this (previously qa depended only on @montr/confirm/@montr/contracts/@montr/fixtures/@montr/config).

External OWASP Benchmark Harness (E14, closes A29): The internal golden corpus is curated by this product's own team, so a buyer cannot use it to independently verify "provably fewer false positives" (PRD §4) — packages/qa/src/owasp-benchmark.ts and owasp-benchmark-cli.ts (pnpm --filter @montr/qa qa:owasp-benchmark) score this product's REAL pipeline output against the real, independently-curated OWASP Benchmark for Java (owasp.org/www-project-benchmark), parsing OWASP Benchmark's OWN `expectedresults-*.csv` ground-truth format and scoring with OWASP Benchmark's OWN methodology (per-test-case TP/FP/TN/FN → TPR/FPR → the project's own headline "Benchmark score" = TPR − FPR), never this repo's internal scorer or corpus/baseline.json gate. A vendored EXCERPT of the real upstream project — 24 of 2,740 test-case Java files (0.9%), pinned commit `ba2e3f9a29fa3bde6a5c073d679393c9b94f025f`, GPL-2.0 (E14's task brief incorrectly assumed Apache-2.0 — corrected in corpus/owasp-benchmark/README.md) — lives at corpus/owasp-benchmark/, covering the 6 of OWASP Benchmark's 11 categories that map onto this product's Category taxonomy (sqli/cmdi/pathtraver/xss/securecookie/crypto|hash|weakrand; ldapi/xpathi/trustbound have no detector for any language and are honestly excluded from scoring, never silently zeroed). scripts/benchmark-owasp.mjs runs the REAL apps/worker L0-L3 pipeline (real App Map, real Semgrep, real correlation + static confirmation; fake in-process LLM gateway, same convention as scripts/corpus-scan.mjs) against the vendored subset; scripts/benchmark-semgrep.mjs runs raw Semgrep directly (no correlation/confirmation post-processing) against the SAME subset with the same primary OWASP ruleset (`p/owasp-top-ten`) this product's own SAST detector uses, for a real, reproducible competitor head-to-head; scripts/benchmark-codeql.mjs checks for a CodeQL CLI and, since none is installed in this environment, documents the exact `codeql database create`/`analyze` commands and exits without fabricating a score, rather than faking one. **A real measured run found a genuine product bug, not a scaffold gap**: `packages/discovery/src/rulesets/java/index.ts`'s `semgrepRulesets: ["p/java", "p/spring"]` — the Semgrep Registry pack `p/spring` currently 404s (retired/renamed upstream), and Semgrep aborts the ENTIRE invocation (not just that one pack) when one `--config` target 404s, so `selectSemgrepRulesets` silently returns a Java app's SAST detector `[]` candidates in production TODAY, even though Semgrep is installed and reachable and `p/java` alone works fine (verified: swapping in a `p/java`-only runner via the already-supported `LayerRunnerOptions.semgrep` injection point raised confirmed findings from 0 to 5 on this exact subset) — A4's "required detector" fail-loud guard does not catch this failure mode (Semgrep exits with a non-empty JSON body containing an `errors` array, which the runner treats as a valid-if-empty result, not an unavailable binary). Not fixed here (packages/discovery/src/** was out of this change's file scope) — documented as a new, real, higher-priority finding for the next audit pass. The REAL, un-worked-around measured result: montr-secure TPR=0.0%/FPR=0.0%/precision=100.0%/score=0.0 vs raw Semgrep TPR=83.3%/FPR=33.3%/precision=88.2%/score=50.0 on the identical 24-case subset — reported exactly as measured (see corpus/owasp-benchmark/README.md for the full root-cause writeup and the diagnostic evidence). Real tests (packages/qa/src/owasp-benchmark.test.ts) cover the real CSV format parser, the OWASP-methodology scorer, and load-and-validate the actual committed vendored subset.

Self-Scan Dogfooding: Executed via scripts/selfscan.mjs, running the Montr Secure engine directly against its own monorepo to verify pipeline stability and self-detect security concerns.
Unwired-Seam Check (A10): scripts/check-unwired-seams.mjs (pnpm run check:unwired-seams) grep-asserts that every declared "seam" — an exported factory function or gateway method meant to be consumed in production, such as packages/config's resolveFieldEncryptionKey/createKeySource, the LLM gateway's resolvePrompt, createLlmGateway, packages/cost-meter's createBudgetRegistry, and store.falsePositiveMarks — has at least one non-test caller outside the package that defines it. This is a direct regression guard for the "built but unwired" pattern the audit found (real, fully-tested code with zero production callers); a seam intentionally left unconsumed (currently only gateway.stream() — see docs/modules/llm-gateway.md) is listed as a documented, informational exception rather than silently omitted. Blocking in CI, run right after typecheck (build-plan §3.7/§4.7 job in .github/workflows/ci.yml).

Test Frameworks and Tooling
Vitest: Primary test runner configured in vitest.config.ts, resolving internal package source code directly via path aliases to support testing without intermediate build steps.
V8 Coverage: Code coverage engine configured in vitest.config.ts with enforced threshold floors of fifty-five percent statements, sixty-eight percent branches, sixty-one percent functions, and fifty-five percent lines.
Fake LLM Gateway: Provided by packages/fixtures/src/fake-llm.ts, simulating deterministic model responses for triage, correlation, confirmation, and fix generation without external API calls.
Memory Store: In-memory repository implementations provided by packages/state-store/src/memory-store.ts allowing high-speed isolated test runs without requiring running Postgres instances.

Running Tests Locally
Standard Suite: Execute pnpm test from the repository root to run all unit, integration, and invariant tests.
Coverage Report: Execute pnpm test:coverage to run the test suite and evaluate V8 code coverage against mandatory thresholds.
Turbo Parallel Tests: Execute pnpm test:turbo to run tests across individual workspace packages using Turborepo caching.
End-to-End Test: Execute pnpm e2e to run a full pipeline scan against fixture repositories.
Corpus Benchmark: Execute pnpm corpus:scan to run the golden corpus benchmark and generate precision/recall metrics.
Smoke Integration: Execute pnpm smoke to run an API and worker integration smoke test.
Unwired-Seam Check: Execute pnpm run check:unwired-seams to verify every declared production seam still has a real, non-test caller.
Model-Variance Matrix: Execute pnpm --filter @montr/qa qa:variance to run the REAL, per-model accuracy-cliff harness (A23); pass -- --variance-selfcheck for the old tautological self-check instead.
External Benchmark: Execute node scripts/benchmark-owasp.mjs then node scripts/benchmark-semgrep.mjs, then pnpm --filter @montr/qa qa:owasp-benchmark -- --our-findings owasp-benchmark-scan.json --semgrep-json owasp-benchmark-semgrep.json to run the OWASP Benchmark harness (E14/A29) and print the head-to-head comparison report.
