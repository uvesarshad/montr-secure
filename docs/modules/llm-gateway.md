# Module: LLM Gateway and Cost Metering

Last updated: auto

Overview
The LLM Gateway and Cost Meter modules (implemented across packages/llm-gateway and packages/cost-meter) provide a unified, provider-agnostic interface for executing language model operations across the pipeline. Montr Secure enforces a strict bring-your-own-key (BYO-key) architecture, where customer credentials communicate directly with upstream providers — Anthropic, AWS Bedrock, GCP Vertex AI, Azure OpenAI, and (A3) direct OpenAI, Google Gemini, xAI Grok, Moonshot Kimi, Zhipu GLM, and DeepSeek — without intermediary proxies. Cost is treated as a first-class operational metric, tracking token expenditures in real time and enforcing hard-halt budget limits before budget overruns occur.

Entry Points and Gateway Architecture
Gateway Client: packages/llm-gateway/src/gateway.ts exports the LlmGateway service used by all pipeline layers to execute completions.
Cost Meter Service: packages/cost-meter/src/meter.ts exports the CostMeter class, which measures prompt, completion, and cached token usage per request.
Provider Adapters: Located in packages/llm-gateway/src/adapters, containing dedicated API drivers for Anthropic, Bedrock, Vertex AI, and Azure OpenAI, plus (A3) one generic OpenAiCompatibleAdapter covering the six direct-key OpenAI-wire-format providers — see Ten-Provider Support below.

Ten-Provider Support (A3)
packages/contracts/src/llm.ts's ProviderSchema now admits ten values: the original four (anthropic, bedrock, vertex, azure), each with its own adapter, plus openai, google, xai, moonshot, zhipu, deepseek — all reached through ONE new packages/llm-gateway/src/adapters/openai-compatible.ts (OpenAiCompatibleAdapter): the `openai` SDK pointed at a per-provider baseURL with a Bearer key, same lazy-import/thin-adapter/threaded-egress-guard convention as every other adapter. adapters/index.ts's createAdapter switch grew a case per new provider, each resolving its `{baseUrl, host}` default from a small OPENAI_COMPATIBLE map (overridable via config.llm.endpoint, same as every other provider).

Model Matrix and Tier Routing
Triage Tier: Managed by packages/llm-gateway/src/models.ts. Routes high-volume filtering in Layer 1 and candidate grouping in Layer 2 to fast, cost-effective models. RECOMMENDED_MODEL_MATRIX.triage (packages/contracts/src/llm.ts) — and so the unconfigured default for MONTR_MODEL_TRIAGE / config.llm.modelMatrix.triage — is claude-haiku-4-5, the undated canonical id (A11; was the dated claude-haiku-4-5-20251001 snapshot). packages/cost-meter/src/pricing.ts's normalizeModelId strips a trailing -YYYYMMDD suffix, so either form still prices identically off the same rate-card row (MODEL_COST_RATES intentionally keeps the dated entry — see Pricing Engine below).
Default Tier: Routes Layer 0 AST extraction and Layer 4 patch synthesis to balanced models (such as Claude Sonnet 5).
Confirmation Tier: Routes Layer 3 interprocedural static taint proofs to high-capacity reasoning models. RECOMMENDED_MODEL_MATRIX.confirmation is now claude-opus-5, the current flagship (A11; was claude-opus-4-8, which remains on the rate card and floor-passing, and can still be set explicitly via MONTR_MODEL_CONFIRMATION). The gateway enforces an accuracy floor, warning operators if sub-floor models are selected.
Model-Fallback Cascade (A11): config.llm.fallbackModel (packages/config/src/schema.ts, env MONTR_LLM_FALLBACK_MODEL) names one alternate model id — e.g. a Sonnet-class fallback for an Opus confirmation call. Previously a failing model was retried on itself (packages/llm-gateway/src/retry.ts's withRetry, per the RetryPolicy) and then the call failed outright, with no cascade to another model. packages/llm-gateway/src/gateway.ts's complete() now runs withRetryAndFallback: the resolved primary model still gets the FULL retry policy unchanged, and only once that is exhausted (or the primary fails immediately on a non-retriable error) does the gateway retry the SAME request against fallbackModel — exactly one bare attempt, no backoff, no further retries, so the cascade is bounded and never infinite. A fallback id identical to the primary is skipped (no self-fallback). Unset (default): today's fail-outright-after-retries behavior is unchanged. Each fallback attempt increments the llm_gateway.model_fallback error metric via getMetrics().recordError (the same pattern cost-meter's unknown-model fallback uses) and logs a structured llm.model_fallback warning with fromModel/toModel/purpose/layer/scanId. stream() does not participate in retry or fallback (unchanged — it never called withRetry either).
Dynamic Model-Tier Escalation (E9): a DIFFERENT mechanism from the fallback cascade above — fallback triggers on FAILURE/exhausted-retries and swaps to a client-configured alternate MODEL; escalation triggers on a SUCCESSFUL but low-confidence response and walks UP the configured tier ladder (triage → default → confirmation). OFF by default via the new CreateGatewayOptions.escalation (packages/llm-gateway/src/gateway.ts), following the same constructor-level opt-in pattern as budgetRegistry/fallbackModel — a caller that omits it sees complete() behave byte-for-byte identically to before this option existed. When enabled, packages/llm-gateway/src/escalation.ts's evaluateConfidence judges each response low-confidence using, in order: (1) a self-reported top-level confidence field (number in [0,1], or "low"/"medium"/"high") in a JSON-mode response body — forward-compatible with a future prompt or E4's verifier-vote spread emitting this, but nothing does today; (2) stopReason === "refusal" — the model explicitly declining to answer, a proxy that needs zero prompt changes; (3) a JSON-mode response whose body fails JSON.parse — an "uncertain"/malformed response, related to but logged separately from the existing llm_gateway.response_parse_failure metric (A13). Only a request that resolved via an explicit request.tier — NOT a pinned request.model — is eligible (models.ts's nextTier walks TIER_ORDER; a request already at the top configured tier, or one with no explicit tier at all, never escalates). Each escalation attempt is capped by escalation.maxEscalations (default 2 — the full 3-tier ladder) and always additionally bounded by nextTier returning undefined past confirmation, so cost stays predictable regardless of chain length; every escalated request still passes through the SAME retry policy, model-fallback cascade, and pre-call budget guard as any other call — the mechanisms compose rather than replace one another. Each attempt increments the llm_gateway.model_escalation error metric and logs a structured llm.model_escalation warning (fromTier/toTier/reason/confidence/purpose/layer/scanId); the final returned response carries the last evaluated confidence on LLMResponse.confidence (additive field, packages/contracts/src/llm.ts — undefined whenever escalation isn't enabled). NOT wired into any pipeline layer: escalation is a constructor-level option (like fallbackModel), so actually turning it on for a layer requires an apps/worker/src/main.ts change to createLlmGateway's construction, which was outside this change's scoped file list (packages/llm-gateway/src/**, packages/contracts/src/llm.ts). packages/discovery/src/triage.ts's existing `{ tier: "triage" }` request already qualifies for escalation with zero changes to that file the moment a future change enables it at construction — built and fully tested standalone (packages/llm-gateway/src/escalation.test.ts), mirroring how A10/A31 handled gateway streaming and the Batch API.

Structured Outputs and Parse-Failure Metric (A13)
Real JSON-Schema Enforcement: packages/llm-gateway/src/structured-output.ts's resolveStructuredOutputSchema resolves a real JSON schema for responseFormat:"json" requests, keyed by request.metadata.purpose — a per-purpose map derived from each real call site's OWN already-existing parsed-JSON expectations (appmap/src/llm.ts, discovery/src/triage.ts, correlation/src/llm.ts, confirm/src/static.ts, fix/src/edits.ts's A14 edit-list contract), so all five real callers get real structured-output enforcement with ZERO changes to those packages. request.responseSchema (additive) is an explicit override for a future caller with no purpose-keyed default. Anthropic/Bedrock send it as output_config.format:{type:"json_schema",schema}; Vertex sends generationConfig.responseMimeType/responseSchema; Azure upgrades response_format from json_object to json_schema when a schema resolves. No schema is requested when request.tools is set (a tool-calling turn's response is the tool call, not JSON text).
Parse-Failure Metric: packages/llm-gateway/src/gateway.ts's private maybeRecordParseFailure (called from complete(), after every real response) attempts JSON.parse(response.content) whenever responseFormat is "json" and no tool call was returned; a failure increments the llm_gateway.response_parse_failure error metric via getMetrics().recordError and logs a structured llm.response_parse_failure warning (provider/model/purpose/layer). Checked centrally at the gateway boundary rather than duplicated per layer — it fires even when a caller's own try/catch fallback (e.g. confirm/src/static.ts's safeJson, correlation/src/llm.ts's parseCorrelationResponse) "succeeds" with an empty/degraded result, so a deployment-wide collapse in LLM contribution can't hide behind five different fail-safe paths. stream() is not covered (no layer calls it — A10).

Key-Tier Safety Guard and Prompt Registry
Key-Tier Guard: packages/llm-gateway/src/keytier.ts inspects API key patterns and metadata to identify consumer or non-enterprise keys that may retain customer data, logging warnings or blocking execution based on configuration.
Prompt Registry: packages/llm-gateway/src/prompts.ts manages versioned prompt templates stored in the PromptVersion database table, allowing regression tracking and template optimization. MontrLlmGateway.resolvePrompt(name, fallback, {clientId}) is the call surface; it resolves the active DB version for name (client-scoped override first, else the global version) or returns fallback unchanged when none is active — a lookup failure is logged and also treated as "use fallback", never thrown. Wired (A10): all five real prompt call sites now call it instead of using their hardcoded constant directly — packages/appmap/src/llm.ts (appmap.auth_boundaries.system), packages/discovery/src/triage.ts (triage.system), packages/correlation/src/correlate.ts (correlation.system), packages/confirm/src/static.ts's runLlmReview (confirm.static_review.system), and packages/fix/src/generate.ts (fix.system) — so creating and activating a PromptVersion row for one of those names now actually changes production behavior with zero code deploy. packages/contracts/src/llm.ts's LLMGateway interface gained an optional resolvePrompt method (structurally matching MontrLlmGateway's) so every call site's gateway parameter — typed against the base contract, not the concrete class — compiles without a cast; a fake/test gateway that omits it remains a valid LLMGateway (the call sites use resolvePrompt?.(...) accordingly).
Versioned Prompt Registry, additive (E15): the underlying store already carried real version numbers (state-store's PromptVersion.version + @@unique([name, version]), and PromptVersionRepositoryImpl's createVersion/listVersions/markActive) — the gap was that packages/llm-gateway could only ever resolve "whichever version is ACTIVE," with no seam to pin a SPECIFIC version. packages/llm-gateway/src/prompts.ts's PromptVersionSource interface gained an optional listVersions method (a strict widening — PromptVersionRepositoryImpl already satisfies it structurally, since its PromptVersionRecord return type is a superset of the widened PromptVersionSourceRecord) plus a new pure resolvePromptVersionTemplate(source, name, version, fallback) function, and MontrLlmGateway gained a matching resolvePromptVersion(name, version, fallback, opts) method mirroring resolvePrompt's fail-safe contract exactly (never throws; any lookup gap resolves to fallback). New packages/llm-gateway/src/prompt-version-registry.ts's InMemoryPromptVersionRegistry is a Map-backed PromptVersionSource with the same (name, version, isActive) shape as the real repository, for offline eval/tests without Postgres. None of the five real call sites were touched — they still resolve the ACTIVE version via resolvePrompt, unchanged. See Eval-Driven Prompt Optimization in docs/infra/testing.md for how packages/qa's new prompt-eval.ts consumes this seam to A/B a candidate version against the golden corpus before promotion.
Cross-Scan Memory Injection (E8): a SEPARATE mechanism from the prompt registry above — the registry swaps a prompt's fixed TEMPLATE; this appends per-scan, per-repo learned FACTS on top of whatever template resolved. apps/worker/src/runners.ts's withLearnedFactsContext wraps the gateway instance passed into Layer 1 discovery, Layer 2 correlation, and Layer 3 confirmation (not the gateway package itself, and not Layer 0 or Layer 4): its complete() intercepts a request whose metadata.purpose is triage, correlation, or confirmation and metadata.clientId matches the wrapped scan's client, and appends a bounded, additive context block (packages/state-store's LearnedFact rows for that client and repo, plus a read-only merge of A10's FalsePositiveMarkRepository signals as a confirmed_false_positive line) to request.system — never replacing the resolvePrompt-resolved template, and passed through unchanged for every other purpose or client. Capped at LEARNED_FACT_CONTEXT_LIMIT (10) total lines so an old, heavily-annotated repo cannot blow the prompt budget; a repo with no prior facts produces a byte-identical request to before this change. This wrapper lives in apps/worker rather than packages/llm-gateway or packages/correlation/confirm/discovery because those three layer packages were out of this change's file scope — see docs/api/database.md's Cross-Scan Memory section and docs/modules/discovery.md for the data model and the alternative in-package wiring point this deliberately avoided touching.

Cost Metering and Hard-Halt Enforcement
Pricing Engine: packages/cost-meter/src/pricing.ts maintains up-to-date per-million token pricing tables across input, output, and cached prompt tokens for each supported model. The reference rate card lives in packages/contracts/src/llm.ts (MODEL_COST_RATES) and currently covers claude-opus-5, claude-opus-4-8, claude-fable-5, claude-sonnet-5, and claude-haiku-4-5-20251001. priceUsageUsd's new opts.batch (A31, BATCH_DISCOUNT_MULTIPLIER = 0.5) halves the computed price — applied on TOP of, not instead of, the cache-read/cache-write multipliers, matching how batch + prompt caching stack in practice — and MeterEntry/CostMeter.record() gained a matching batch flag so a Batch API result is priced correctly once recorded.
Fail-Closed Unknown-Model Pricing: priceUsageUsd in packages/cost-meter/src/pricing.ts never returns $0 for a model id absent from the rate card. It bills at UNKNOWN_MODEL_FALLBACK_RATE (packages/contracts/src/llm.ts) — a conservative ceiling set to the highest input/output rate on the whole card (currently claude-fable-5's $10/$50 per million) — so an unlisted BYO model can never defeat the budget hard-halt by pricing at zero. Every fallback hit increments the cost_meter.unknown_model_rate error metric via packages/telemetry's getMetrics().recordError, and optionally logs a structured warning if a Logger is passed through CostMeterOptions.logger (threaded from packages/cost-meter/src/meter.ts's createCostMeter into both live metering and the pre-scan estimator in estimate.ts).
Partner Pricing Normalization: packages/cost-meter/src/pricing.ts's normalizeModelId strips the Bedrock anthropic. prefix, a Vertex @date snapshot suffix, and a -fast/dated-snapshot suffix before rate-card lookup, so Bedrock and Vertex requests for a first-party Anthropic model (for example anthropic.claude-opus-5 or claude-fable-5@20260101) resolve to the same first-party rate-card row without a separate partner rate entry. The Azure OpenAI adapter (packages/llm-gateway/src/adapters/azure.ts) treats its model id as an opaque, client-configured deployment name with no fixed Azure model literals in the codebase, so there is no enumerable Azure model list to add rate-card rows for — an Azure deployment name always falls through to the fail-closed fallback rate unless a client's own model id happens to match a Claude id.
Pre-Scan Estimation: packages/cost-meter/src/estimate.ts models projected token consumption based on repository size, route counts, and AST complexity during Layer 0. A19: its per-unit constants (files*300 + routes*250, etc.) remain UNCALIBRATED heuristics, documented as such in-code — no real captured per-layer prompt-size data exists anywhere in this repo to calibrate against (checked: corpus/baseline.json tracks recall/precision/FP-rate only; no scan-log/fixture captures real prompt byte counts). See Token Counting and Batch API below.
Real-Time Metering (A32): packages/llm-gateway/src/gateway.ts's private account() — called after every completed complete()/stream() invocation — records the call's real token usage into the per-scan CostMeter resolved from budgetRegistry.get(request.metadata.scanId).meter, the SAME instance packages/orchestrator/src/controller.ts registers before each layer job, hands to the layer as ctx.costMeter, and reads afterward in its between-layers enforceBudget check. Before A32, account() only wrote to the gateway's constructor-level costMeter option, which apps/worker/src/main.ts never set — real spend never accumulated anywhere the orchestrator or the pre-call guard could see, and enforceBudget was permanently evaluating $0 spent. account() also still records into the standalone opts.costMeter when one is configured (legitimate for callers that don't use budgetRegistry — tests, one-off/non-worker tooling), skipping the duplicate record() call if that instance happens to be the same object as the registry-resolved meter.
Hard-Halt Ceiling: If cumulative dollar or token expenditure breaches configured limits (such as MONTR_BUDGET_MAX_USD), the meter throws a BudgetExceededError, signaling the orchestrator to halt analysis immediately and emit a partial report.

Pre-Call Budget Guard: packages/llm-gateway/src/gateway.ts's complete() and stream() methods estimate the pending call's cost (input tokens via estimateTokens, output tokens conservatively taken as the request's maxTokens, the worst case the model may spend) before dispatching to a provider adapter. When a BudgetRegistry is supplied at gateway construction, the estimate is checked against the scan's live CostMeter and effective BudgetPolicy, looked up by the request's metadata.scanId; a call whose spend-so-far plus its own estimated cost would clear the ceiling is refused with a BudgetExceededError (details.phase: "pre_call") before any provider is contacted. This is additive to, not a replacement for, the between-layers checkBudget call in packages/orchestrator/src/controller.ts — the pre-call guard stops a single call from ever reaching the wire mid-layer; the between-layers check still catches drift between estimates and provider-reported actuals. The guard only fires when policy.enforcement is "hard_halt". As of A32, the "spend-so-far" half of that comparison is real accumulated spend (see Real-Time Metering above), not a permanently-zero reading.
Budget Registry Wiring: packages/cost-meter/src/registry.ts exports createBudgetRegistry — a shared in-memory map, keyed by scanId, holding each running scan's CostMeter plus its effective BudgetPolicy. apps/worker/src/main.ts constructs one registry per worker process and passes the same instance to createLlmGateway (as budgetRegistry, for the gateway to both read the ceiling from and write real usage into) and into startWorker's WorkerRuntimeDeps (as budgetRegistry, forwarded to createOrchestrator, for the controller to write to). packages/orchestrator/src/controller.ts registers a scan's meter and policy immediately before executing each layer job and unregisters on scan cleanup; that meter comes from the controller's own getMeter(scanId) cache, so it is the identical instance registered into the registry, handed to the layer as ctx.costMeter, and read by enforceBudget.
Real Layer Call Sites: packages/appmap/src/llm.ts, packages/discovery/src/triage.ts, packages/correlation/src/correlate.ts, packages/fix/src/generate.ts, and packages/confirm/src/static.ts's runLlmReview all set metadata.scanId on every real gateway.complete() call — required for both the pre-call guard's lookup and account()'s real-time recording to resolve a scan's registered meter. The same five sites also now call resolvePrompt (see Prompt Registry above, A10).

Token Counting and Batch API (A19, A31 item 3)
Real Token Counting (A19): MontrLlmGateway.countTokens(request) calls the adapter's real countTokens (packages/llm-gateway/src/adapters/anthropic.ts, Anthropic's messages.countTokens / POST /v1/messages/count_tokens, via mapping.ts's buildAnthropicCountTokensBody) when available, falling back — logging a warning, never throwing — to estimateTokens's chars/4 heuristic for Bedrock/Vertex/Azure (no real counting endpoint wired for those today) or on a real-call failure. Deliberately NOT wired into the A2 pre-call budget guard: assertPreCallBudget still calls the fast local estimateTokens on every gated complete()/stream() — a real per-call network round-trip on that hot path would add latency to every LLM call in the pipeline for a marginal accuracy gain over a heuristic that already errs conservative (over-estimating input tokens is the safe failure direction for a guard whose job is to refuse BEFORE dispatch). countTokens() is for callers that want a precise, provider-verified count and can afford the round-trip (tooling, calibration, a future non-hot-path caller).
Estimate-vs-Actual Validation (A19 item 3): packages/llm-gateway/src/estimate-variance.test.ts computes estimateScanCost's projection for a representative synthetic scan against an "actual" built from real per-layer request shapes (appmap/src/llm.ts's route summary, correlation/src/llm.ts's CorrelationFacts, confirm/src/static.ts's runLlmReview payload) counted via the gateway's own estimateTokens and priced via priceUsageUsd — replacing DOD.md item 6's previous ≈$0 concession with a real, non-trivial number. Measured result: the realistic actual lands roughly 5x BELOW the projection at this scenario's scale (safe over-provisioning direction, not PRD §19's exact ±15% — see the test's comments for why: L0's formula scales with file count though the real Layer 0 call never sends file content, and L2/L3's per-unit constants assume larger prompts than the real call sites' compact JSON). The test asserts order-of-magnitude agreement and that the estimate never sits dangerously below a plausible actual, rather than fabricating a match to the exact ±15% figure.
Batch API (A31 item 3): MontrLlmGateway gained submitBatch()/pollBatch()/getBatchResults() (packages/llm-gateway/src/batch.ts's LLMBatchRequestItem/LLMBatchHandle/LLMBatchStatus/LLMBatchResultItem types), delegating to adapter-level submitBatch/pollBatch/getBatchResults (adapters/types.ts) implemented only by AnthropicAdapter today (adapters/anthropic.ts, the real messages.batches.create/retrieve/results endpoints) — other providers throw NotImplementedError. getBatchResults(batchId, {metadataByCustomId}) normalizes each row into LLMResponse shape (latencyMs: 0) and, when the caller supplies a customId→LLMCallMetadata map, records each succeeded result into that scan's registry-resolved CostMeter at the batch-discounted rate (see Pricing Engine above) — the gateway deliberately does NOT cache this association itself across calls, since a real batch may be polled by a different process/restart than the one that submitted it (results are retained up to 29 days). NOT wired into any pipeline layer: the orchestrator's FSM is built around synchronous layer completion, which a job that may take up to 24h to resolve cannot fit without deeper resumability work; Layer 4 fix generation (packages/fix/src/generate.ts, multiple confirmed findings, no user waiting synchronously) is the best-fit future consumer but is outside this change's scoped file list. Built and fully tested (packages/llm-gateway/src/adapters/capabilities.test.ts, gateway.test.ts) so the capability exists for a future layer or an offline/bulk consumer (e.g. a corpus-scan mode), mirroring how A10 handled gateway streaming — verified working, honestly reported as not-yet-consumed.

Constraints and Edge Cases
AGENT NOTE: Source SDKs for LLM providers are strictly confined to packages/llm-gateway. No other package or application may import provider SDKs directly.
AGENT NOTE: priceUsageUsd must never return $0 for an unrecognized model id — see Fail-Closed Unknown-Model Pricing above. Any new caller of priceUsageUsd should pass a Logger where one is available so the unknown-model warning surfaces.
AGENT NOTE: Omitting budgetRegistry from createLlmGateway leaves only between-layers budget enforcement (today's prior behavior, unchanged) — and account() then has no registry to record real spend into unless a standalone opts.costMeter is configured. A caller that wires createOrchestrator's budgetRegistry must pass the SAME instance to createLlmGateway or both the pre-call guard AND real-time accounting silently no-op for that scan.
AGENT NOTE: Every real gateway caller MUST set request.metadata.scanId — see Real Layer Call Sites above. Without it, account() has nothing to look up in budgetRegistry and that call's spend is silently dropped from per-scan tracking (unless a standalone costMeter is configured).
AGENT AVOID: Never disable budget hard-halt enforcement in production environments.
AGENT NOTE (A8 output caps): correlation's maxTokens raised 512→2048 (packages/correlation/src/llm.ts) and confirmation's maxTokens raised 1024→4096 (packages/confirm/src/static.ts's runLlmReview) — output-token headroom to reason, not a cost control (cost is governed by the budget meter/hard-halt above, independent of the maxTokens ceiling).
