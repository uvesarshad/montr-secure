# Module: Layer 5 Reporting, Compliance, and VCS Integration

Scope: Final report assembly, executive summaries, compliance mapping (SARIF, SOC2, ISO, OWASP), and automated pull request generation.
Rendering context: Server
Project tier: 4
Last updated: auto

Overview
The Reporting and VCS module executes Layer 5 of the analysis pipeline within packages/report. It aggregates confirmed findings, exploit proof artifacts, synthesized diff patches, and cost accounting data into a unified, audit-grade Report document. Layer 5 produces compliance mappings across standard regulatory frameworks (SARIF, SOC2 Type II, ISO27001, OWASP Top 10) and, when authorized by an Approver, opens automated remediation pull requests on GitHub or GitLab for auto-eligible fixes.

Entry Points and Core Runners
Layer 5 Runner: packages/report/src/report-builder.ts exports runLayer5Report, which constructs the finalized report document, records posture snapshots, and triggers automated PR workflows.
Queue Execution: apps/worker/src/runners.ts pulls Layer 5 jobs from BullMQ and executes report generation upon completion of Layer 4.

Key Components and Exporters
Report Builder: packages/report/src/report-builder.ts compiles confirmed findings, proof traces, generated patches, unconfirmed finding appendixes, and token metrics into a monolithic JSON Report persisted in Postgres.
Headline Formatter: packages/report/src/headline.ts generates clear executive summaries highlighting exploit-confirmed issues while explicitly omitting raw candidate counts.
Compliance Exporters: Located in packages/report/src/exports:
SARIF Exporter (packages/report/src/exports/sarif.ts): Transforms findings into OASIS Static Analysis Results Interchange Format (SARIF v2.1.0) JSON for CI/CD integration. `driver.rules[].properties.tags`/`results[].properties` carry CWE (`external/cwe/<id>`), OWASP (`OWASP-<id>`), and, since B2, MITRE ATT&CK/ATLAS technique ids (`external/attack/<id>`, e.g. `external/attack/t1190`) per finding category.
SOC2 Exporter: Maps confirmed vulnerabilities to SOC2 Common Criteria security and availability controls.
ISO27001 Exporter: Maps findings to ISO/IEC 27001:2022 Annex A security controls.
OWASP Mapper: Maps findings to OWASP Top 10 2021 categories.
MITRE ATT&CK Mapper (B2): packages/contracts/src/mitre.ts owns the exhaustive `CATEGORY_MITRE_TECHNIQUES: Record<Category, readonly string[]>` (real Enterprise ATT&CK ids, plus MITRE ATLAS's `AML.T0051` for `prompt_injection` — Enterprise ATT&CK has no dedicated technique for it) and `mitreTechniqueIdsForCategory`/`mitreTechniquesForCategory` accessors, mirroring `packages/report/src/exports/controls.ts`'s SOC2/ISO27001 `Record<Category, ...>` pattern. `packages/report/src/exports/mitre-attack.ts` is the standalone report-surfacing layer (per-finding technique mapping + a technique -> finding coverage index, JSON-renderable via `renderMitreAttackJson`) — not yet wired into the `exports/index.ts` format registry or `report-builder.ts` (a later wave wires it in alongside the other blue-team capabilities).
Threat Model Report (B7): packages/report/src/exports/threat-model.ts renders the persisted `AppMap.threatModel` (E6/B1 — `ThreatModel` from packages/contracts/src/threat-model.ts) into the REVIEWABLE deliverable: `buildThreatModelReport` produces a plain-data model (trust boundaries, a STRIDE roll-up table, the plausible attack-surface categories, abuse cases, and a grounded plain-language summary), rendered via `renderThreatModelReportJson` and `renderThreatModelReportMarkdown`. It never re-derives anything — E6 (`packages/appmap/src/threat-model.ts`) is the only place `ThreatModel` is computed; this module is a pure reader. It also introduces STRIDE classification itself (additive, in `@montr/contracts` and `@montr/appmap`, not this package — see docs/modules/appmap.md's Threat-Model Derivation section): `AttackSurfaceEntry.stride` (from the existing per-category plausibility, via `strideForCategory`, suppressed to `[]` when plausibility is `"none"`) and `TrustBoundary.stride` (from `buildTrustBoundaries`'s new `strideForTrustBoundary`, grounded in that boundary's own routes/auth-state/route→model fan-out — a public write-capable boundary gets Spoofing + Tampering + Elevation of Privilege + Repudiation; a resolved-authentication boundary with no such fan-out gets `[]`, deliberately never a six-for-six dump). Denial of Service is intentionally never derived at the trust-boundary level: the App Map has no rate-limit/throughput signal at Layer 0, so a DoS verdict from route/auth shape alone would be a guess. `scopeHints` is deliberately dropped from the rendered artifact — it is E6's internal prioritization signal, not reader-facing evidence. Like `mitre-attack.ts`, NOT yet wired into `exports/index.ts`'s registry or `report-builder.ts` — B10 wires it in.
Posture Snapshotter: Derives a PostureSnapshot record from confirmed findings, tracking security posture trends over time.
Detection-Rule Generation (B3/B4): packages/report/src/detection-rules (see generate.ts's header for the full picture) builds real Sigma/OTel/SIEM detection rules PLUS a human-readable log-signature narrative per `ConfirmedFinding`, all rendered from one shared `RuleContext` (context.ts) so all outputs express the same detection logic. For a live-DAST-proven finding the context recovers the ACTUAL exploit signature by diffing the transcript's last (most-refined) exchange against its first/baseline exchange — real captured payload, no per-category guessing. For a static-proof-only finding it falls back to well-known category payload markers plus the App Map route (file+line match, mirroring `packages/confirm/src/static.ts`'s own `findRoute`, reimplemented locally since it isn't exported); with no resolvable route at all it degrades further to a `file_event`-category rule keyed on `finding.location.file`. `sigma.ts` emits real Sigma YAML (`logsource`/`detection`/`condition`/`level`/`tags`); `otel.ts` emits an OTTL (OpenTelemetry Transformation Language) boolean condition over semconv attribute names — the real expression language an OpenTelemetry Collector filter/transform processor evaluates; `siem.ts` emits Splunk SPL. `narrative.ts` builds the B4 `DetectionLogSignature` (`packages/contracts/src/blue-team.ts`, additive `DetectionRule.logSignature` field) — concrete fields, the exact log pattern, and an exhaustive `Record<Category, ...>`-enforced, finding-specific false-alarm-sources sentence (e.g. "an internal reporting/BI tool... can contain quotes... scope to non-admin-role sessions" for `sql_injection`), never generic boilerplate. `mitreTechniques` defaults to B2's `mitreTechniqueIdsForCategory` (still overridable). `generateDetectionRules` is pure; `persistDetectionRules` is the thin `StateStore.detectionRules.create` (B1) wrapper, row-scoped by `clientId`. STANDALONE — not called from `report-builder.ts` (A10's "built but unwired, honestly documented" precedent); B10 wires a detection-engineering report section in a later wave.

Automated Pull Request Flow in packages/report/src/vcs.ts and auto-fix.ts
Auto-Fix Controller: packages/report/src/auto-fix.ts evaluates the scan gateState. If auto-fix is enabled, the fix gate is approved, and fixes are marked auto-eligible, it invokes the VCS provider.
VCS Provider: packages/report/src/vcs.ts supports GitHub and GitLab. It creates a dedicated remediation git branch (such as montr/fix-scan-id), applies unified diff patches, commits changes, and opens a formal Pull Request with an explanatory description and proof-of-fix test summaries.
Pull Request Tracking: Creates a PullRequest record in Postgres linked to the parent Scan and updated Fix records.

Constraints and Edge Cases
AGENT NOTE: Auto-fix is strictly PR-only. Direct commits to base branches are permanently blocked by design.
AGENT AVOID: Never include unconfirmed candidate counts in executive summary headlines.
