# Module: Layer 5 Reporting, Compliance, and VCS Integration

Scope: Final report assembly, executive summaries, compliance mapping (SARIF, SOC2, ISO, OWASP), and automated pull request generation.
Rendering context: Server
Project tier: 4
Last updated: auto

Overview
The Reporting and VCS module executes Layer 5 of the analysis pipeline within packages/report. It aggregates confirmed findings, exploit proof artifacts, synthesized diff patches, and cost accounting data into a unified, audit-grade Report document. Layer 5 produces compliance mappings across standard regulatory frameworks (SARIF, SOC2 Type II, ISO27001, OWASP Top 10) and, when authorized by an Approver, opens automated remediation pull requests on GitHub or GitLab for auto-eligible fixes.

Entry Points and Core Runners
Layer 5 Runner: packages/report/src/report-builder.ts exports runLayer5Report, which constructs the finalized report document, records posture snapshots, and triggers automated PR workflows.
Queue Execution: apps/worker/src/runners.ts pulls Layer 5 jobs from BullMQ and executes report generation upon completion of Layer 4.

Key Components and Exporters
Report Builder: packages/report/src/report-builder.ts compiles confirmed findings, proof traces, generated patches, unconfirmed finding appendixes, and token metrics into a monolithic JSON Report persisted in Postgres.
Headline Formatter: packages/report/src/headline.ts generates clear executive summaries highlighting exploit-confirmed issues while explicitly omitting raw candidate counts.
Compliance Exporters: Located in packages/report/src/exports:
SARIF Exporter (packages/report/src/exports/sarif.ts): Transforms findings into OASIS Static Analysis Results Interchange Format (SARIF v2.1.0) JSON for CI/CD integration. `driver.rules[].properties.tags`/`results[].properties` carry CWE (`external/cwe/<id>`), OWASP (`OWASP-<id>`), and, since B2, MITRE ATT&CK/ATLAS technique ids (`external/attack/<id>`, e.g. `external/attack/t1190`) per finding category.
SOC2 Exporter: Maps confirmed vulnerabilities to SOC2 Common Criteria security and availability controls.
ISO27001 Exporter: Maps findings to ISO/IEC 27001:2022 Annex A security controls.
OWASP Mapper: Maps findings to OWASP Top 10 2021 categories.
MITRE ATT&CK Mapper (B2): packages/contracts/src/mitre.ts owns the exhaustive `CATEGORY_MITRE_TECHNIQUES: Record<Category, readonly string[]>` (real Enterprise ATT&CK ids, plus MITRE ATLAS's `AML.T0051` for `prompt_injection` — Enterprise ATT&CK has no dedicated technique for it) and `mitreTechniqueIdsForCategory`/`mitreTechniquesForCategory` accessors, mirroring `packages/report/src/exports/controls.ts`'s SOC2/ISO27001 `Record<Category, ...>` pattern. `packages/report/src/exports/mitre-attack.ts` is the standalone report-surfacing layer (per-finding technique mapping + a technique -> finding coverage index, JSON-renderable via `renderMitreAttackJson`). NOW WIRED (B10): `report-builder.ts`'s `buildBlueTeamReport` calls `buildMitreAttackSection` against the just-assembled core report and embeds the result at `Report.blueTeam.mitreAttack.{findings,coverage}`.
Threat Model Report (B7): packages/report/src/exports/threat-model.ts renders the persisted `AppMap.threatModel` (E6/B1 — `ThreatModel` from packages/contracts/src/threat-model.ts) into the REVIEWABLE deliverable: `buildThreatModelReport` produces a plain-data model (trust boundaries, a STRIDE roll-up table, the plausible attack-surface categories, abuse cases, and a grounded plain-language summary), rendered via `renderThreatModelReportJson` and `renderThreatModelReportMarkdown`. It never re-derives anything — E6 (`packages/appmap/src/threat-model.ts`) is the only place `ThreatModel` is computed; this module is a pure reader. It also introduces STRIDE classification itself (additive, in `@montr/contracts` and `@montr/appmap`, not this package — see docs/modules/appmap.md's Threat-Model Derivation section): `AttackSurfaceEntry.stride` (from the existing per-category plausibility, via `strideForCategory`, suppressed to `[]` when plausibility is `"none"`) and `TrustBoundary.stride` (from `buildTrustBoundaries`'s new `strideForTrustBoundary`, grounded in that boundary's own routes/auth-state/route→model fan-out — a public write-capable boundary gets Spoofing + Tampering + Elevation of Privilege + Repudiation; a resolved-authentication boundary with no such fan-out gets `[]`, deliberately never a six-for-six dump). Denial of Service is intentionally never derived at the trust-boundary level: the App Map has no rate-limit/throughput signal at Layer 0, so a DoS verdict from route/auth shape alone would be a guess. `scopeHints` is deliberately dropped from the rendered artifact — it is E6's internal prioritization signal, not reader-facing evidence. NOW WIRED (B10): when `BuildReportInput.appMap.threatModel` is present, `buildBlueTeamReport` calls both `buildThreatModelReport` and `renderThreatModelReportMarkdown` and embeds `{present, summary, markdown, raw}` at `Report.blueTeam.threatModel` (`present: false` and no other fields when the App Map carried no threat model).
Posture Snapshotter: Derives a PostureSnapshot record from confirmed findings, tracking security posture trends over time.
Detection-Rule Generation (B3/B4): packages/report/src/detection-rules (see generate.ts's header for the full picture) builds real Sigma/OTel/SIEM detection rules PLUS a human-readable log-signature narrative per `ConfirmedFinding`, all rendered from one shared `RuleContext` (context.ts) so all outputs express the same detection logic. For a live-DAST-proven finding the context recovers the ACTUAL exploit signature by diffing the transcript's last (most-refined) exchange against its first/baseline exchange — real captured payload, no per-category guessing. For a static-proof-only finding it falls back to well-known category payload markers plus the App Map route (file+line match, mirroring `packages/confirm/src/static.ts`'s own `findRoute`, reimplemented locally since it isn't exported); with no resolvable route at all it degrades further to a `file_event`-category rule keyed on `finding.location.file`. `sigma.ts` emits real Sigma YAML (`logsource`/`detection`/`condition`/`level`/`tags`); `otel.ts` emits an OTTL (OpenTelemetry Transformation Language) boolean condition over semconv attribute names — the real expression language an OpenTelemetry Collector filter/transform processor evaluates; `siem.ts` emits Splunk SPL. `narrative.ts` builds the B4 `DetectionLogSignature` (`packages/contracts/src/blue-team.ts`, additive `DetectionRule.logSignature` field) — concrete fields, the exact log pattern, and an exhaustive `Record<Category, ...>`-enforced, finding-specific false-alarm-sources sentence (e.g. "an internal reporting/BI tool... can contain quotes... scope to non-admin-role sessions" for `sql_injection`), never generic boilerplate. `mitreTechniques` defaults to B2's `mitreTechniqueIdsForCategory` (still overridable). `generateDetectionRules` is pure; `persistDetectionRules` is the thin `StateStore.detectionRules.create` (B1) wrapper, row-scoped by `clientId`. NOW WIRED (B10): `buildBlueTeamReport` calls `generateDetectionRules` (pure, no persistence) for every confirmed finding and embeds the full rule set at `Report.blueTeam.detectionEngineering.rules`; `persistDetectionRules` itself remains a separate, un-called I/O helper for a caller that wants to also write the rows via `StateStore.detectionRules`.
Detection Coverage (B6, packages/appmap/src/coverage-analysis.ts): `buildDetectionCoverage` derives the tri-state `DetectionCoverage` verdict (true / false / `"unknown"`) per confirmed finding from the App Map's `telemetrySurfaces` plus any generated `DetectionRule`s. NOW WIRED (B10): `buildBlueTeamReport` calls it with the SAME `DetectionRule[]` it just generated (so a coverage verdict's `detectionRuleId` always references a rule this same report also lists), embedding the result at `Report.blueTeam.detectionEngineering.coverage`. `persistDetectionCoverageForScan` (the I/O-persisting wrapper) remains un-called by report-builder — it is a separate follow-up for whichever wave wires `apps/worker/src/runners.ts`'s Layer 3 runner (see that function's own doc comment).
Attack-Path Graph (B8, packages/correlation/src/attack-paths): `buildAttackPaths` chains >= 2 confirmed findings into a kill chain across three structural conditions (RCE-enables-everything, credential-leaking IDOR/broken-access-control, SSRF-pivots-into-a-different-non-public-route), scored by end-to-end feasibility and ranked (feasibility desc, then severity). NOW WIRED (B10): `buildBlueTeamReport` calls it whenever an App Map is supplied and embeds the ranked `AttackPath[]` at `Report.blueTeam.attackPaths` (`[]` when no App Map, or when no chain condition is satisfied by the confirmed findings — never a fabricated chain).
Hardening Recommendations (B9, packages/hardening/src/generate.ts): `generateHardeningRecommendations` is genuine I/O (a `FileProvider` over the real repo checkout) that `buildReport` deliberately stays free of — mirrors how `fixes`/`costRollup` are already precomputed by earlier layers rather than regenerated inside Layer 5. NOW WIRED (B10) as a precomputed-input pass-through: a caller runs `generateHardeningRecommendations` itself and passes the result as `BuildReportInput.hardeningRecommendations`; `buildBlueTeamReport` embeds it at `Report.blueTeam.hardening.{advisoryOnly: true, recommendations}` — `advisoryOnly` is a load-bearing literal `true`, distinct from `Report.fixStatus`'s code fixes above (B9's architectural boundary: no diff/patch, never auto-applied). `[]` when the caller supplies nothing. REAL CALLER (A13): `apps/worker/src/runners.ts`'s Layer 5 runner is that caller — it builds a real `@montr/discovery` `fsFileProvider` over the same `resolveRepoRoot`-derived checkout Layer 1/4 already use and passes the confirmed findings, degrading to `[]` (not a guess) when no local checkout exists (a remote repo Layer 0 already cleaned up).
Purple-Team Verification (B5, packages/confirm/src/purple-loop.ts): landed the SAME wave as B10. `runPurpleTeamScenario`/`verifyScenarioDetection` run a red-team scenario through the existing gated Layer-3 engine and structurally evaluate every candidate Sigma `DetectionRule` against the resulting transcript; `summarizePurpleTeamRun` reduces a batch of runs to `PurpleTeamRunSummary` (`entries`, `totalScenarios`, `detectedCount`, `undetectedCount`). NOW WIRED (B10) as a precomputed-input pass-through, same pattern as B9: a caller runs the purple-team loop itself and passes `summarizePurpleTeamRun(...).entries` (or any array shaped like `PurpleTeamScenarioSummaryEntryShape`, packages/contracts/src/report.ts) as `BuildReportInput.purpleTeamEntries`; `buildBlueTeamReport` embeds the entries plus derived counts at `Report.blueTeam.purpleTeam`. `[]` (all counts 0) when no purple-team run has happened yet for this scan — never a fabricated verdict. REAL CALLER (A8): that caller is `apps/worker/src/runners.ts`'s Layer 3 runner, not Layer 5 — see docs/modules/confirmation.md's Purple-Team Verification Loop section for the full wiring (why Layer 3, category-based scenario selection, the shared `defaultTransport`). The resulting entries reach Layer 5 only through the orchestrator's in-process `priorOutputs` cache (`Layer3Output.purpleTeamEntries`, additive and non-persisted, packages/contracts/src/layers.ts) — `[]` on a resumed/distributed run where the cache is empty.
Blue-Team Report Assembly (B10): `packages/report/src/report-builder.ts`'s `buildBlueTeamReport` is the single function that performs all six of the above and returns the `BlueTeamReport` shape (`packages/contracts/src/report.ts`) embedded at `Report.blueTeam` by `buildReport`. Every section degrades to an honest empty/absent state — never a guess — when its optional input (`BuildReportInput.appMap`/`hardeningRecommendations`/`purpleTeamEntries`) is omitted. NOW WIRED (A2/A8/A13): `apps/worker/src/runners.ts`'s Layer 5 runner passes all three real inputs — `appMap` via the SAME `resolveAppMap(ctx)` Layers 1-3 already call (A2), `hardeningRecommendations` from a real `generateHardeningRecommendations` call over an actual repo checkout (A13, see the Hardening Recommendations entry above), and `purpleTeamEntries` from Layer 3's purple-team loop via the in-process `priorOutputs` cache (A8, see the Purple-Team Verification entry above). `buildBlueTeamReport` itself was not modified by this wiring — every section's degrade-to-empty behavior above was already correct and already tested; only the caller-side gap is closed.
Detection Coverage as Compliance Evidence (B10, packages/report/src/exports/controls.ts + evidence.ts): `DETECTION_MONITORING_CONTROL_IDS`/`detectionMonitoringControls` name the real SOC 2 (CC7.2 security event monitoring, CC7.3 security event evaluation) and ISO/IEC 27001:2022 (A.8.15 logging, A.8.16 monitoring activities — the 2022 Annex A renumbering of the 2013 edition's A.12.4/A.16) controls this catalog already carried for `insufficient_logging`. `evidence.ts`'s `evidenceRecord` now reads `Report.blueTeam.detectionEngineering` and, for any finding with a VERIFIED coverage verdict (`DetectionCoverage.detected === true` — never merely "a rule exists" or the tri-state `"unknown"`), adds those controls to `EvidenceRecord.controls` as genuine evidence (deduped against the category's own mapping), alongside new `detectionRuleIds`/`detectionCoverageVerified` fields on the record (also columns in the CSV evidence export). This applies to ANY finding category with verified coverage, not only `insufficient_logging`.

Automated Pull Request Flow in packages/report/src/vcs.ts and auto-fix.ts
Auto-Fix Controller: packages/report/src/auto-fix.ts evaluates the scan gateState. If auto-fix is enabled, the fix gate is approved, and fixes are marked auto-eligible, it invokes the VCS provider.
VCS Provider: packages/report/src/vcs.ts supports GitHub and GitLab. It creates a dedicated remediation git branch (such as montr/fix-scan-id), applies unified diff patches, commits changes, and opens a formal Pull Request with an explanatory description and proof-of-fix test summaries.
Pull Request Tracking: Creates a PullRequest record in Postgres linked to the parent Scan and updated Fix records.

Constraints and Edge Cases
AGENT NOTE: Auto-fix is strictly PR-only. Direct commits to base branches are permanently blocked by design.
AGENT AVOID: Never include unconfirmed candidate counts in executive summary headlines.
