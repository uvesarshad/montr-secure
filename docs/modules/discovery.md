# Module: Layer 1 Parallel Discovery

Scope: Multi-engine static analysis, secret detection, dependency reachability scanning, custom rule execution, IaC/Dockerfile/Kubernetes/Terraform scanning, SBOM dependency inventory, and supply-chain risk heuristics.
Rendering context: Server
Project tier: 4
Last updated: auto

Overview
The Discovery module executes Layer 1 of the analysis pipeline within packages/discovery. It runs multiple security analysis engines concurrently against the target codebase to detect potential vulnerabilities, leaked secrets, vulnerable dependencies, and insecure configurations. Output from Layer 1 is normalized into raw CandidateFinding records. These candidate findings are intentionally treated as noisy intermediate evidence and are never surfaced directly in executive report headlines.

Entry Points and Core Runners
Layer 1 Runner: packages/discovery/src/index.ts exports runLayer1Discovery, which coordinates parallel execution of static analyzers, secret detectors, and dependency scanners.
Queue Execution: apps/worker/src/runners.ts pulls Layer 1 jobs from BullMQ and executes discovery against the local repository checkout.

Key Components and Detection Engines
SAST Engine: Located in packages/discovery/src/detectors/sast.ts. Executes Semgrep static analysis rulesets targeting code vulnerabilities across supported programming languages. Uses hosted Semgrep Registry pack IDs (p/owasp-top-ten, p/typescript, p/nextjs, p/react, p/secrets, plus per-language packs from packages/discovery/src/rulesets) by default, or a local ruleset directory when discovery.rulesetsDir is configured (air-gap mode, see Constraints below).
Secret Scanner: Executes Gitleaks to identify hardcoded API keys, private certificates, and credentials within source files and commit history.
Dependency Reachability Scanner: packages/discovery/src/detectors/sca.ts and packages/discovery/src/advisories.ts query Open Source Vulnerabilities (OSV) databases and match manifest versions against published CVE and GHSA advisories. Reachability is call-granularity on TypeScript/JavaScript (A12): collectCalledPackages runs a real ts-morph AST scan checking whether a binding imported from the vulnerable package is actually invoked (called, constructed, or JSX-rendered) anywhere, not merely present in an import/require statement; collectImportedPackages's plain import-presence regex remains only as the fallback when nothing parses as TS/JS.
Custom Rule Engine: packages/discovery/src/custom-rules.ts compiles and executes client-authored Semgrep YAML rules and regex secret detectors persisted in the CustomRule database table.
Triage Normalizer: packages/discovery/src/triage.ts uses the fast triage model (Claude Haiku 4.5) via packages/llm-gateway to normalize multi-tool outputs into standard CandidateFinding entities. Cross-Scan Memory (E8): triage.ts itself is unchanged — apps/worker/src/runners.ts wraps the gateway instance it hands to Layer 1's DiscoveryDeps so a triage request (metadata.purpose "triage") for this client's repo receives an additive learned-facts context block appended to its system prompt, sourced from packages/state-store's LearnedFact rows (custom sanitizer names, framework idioms, operator decisions recorded on an earlier scan of the same repo) — see docs/modules/llm-gateway.md's Cross-Scan Memory Injection section and docs/api/database.md's Cross-Scan Memory section for the full mechanism and its bounded-size cap.
Threat-Model Scope Consumer (E6): packages/discovery/src/threat-model-scope.ts's applyThreatModelScopeHints reads the App Map's threatModel.scopeHints (see docs/modules/appmap.md) after triage and annotates any candidate whose category is a priority category, or whose file belongs to a priority route, with metadata.threatModelPriority, then stable-sorts annotated candidates to the front of the returned list. It never removes a candidate or changes the candidate count — every candidate the deterministic detectors and triage already produced still ships, in the same set, only reordered and annotated.
AI-Application Security Agent (E11): packages/discovery/src/detectors/ai-security.ts's detectAiSecurity scans the TARGET application for five LLM-integration vulnerability shapes: prompt injection surface (unsanitized data reaching an LLM call's system or early messages content), unsafe tool/function exposure (a dangerous tool wired to an LLM call with no visible authorization gate), unescaped LLM output rendered to users (dangerouslySetInnerHTML/innerHTML fed by an LLM response — XSS with the model as the untrusted source), secrets leaking into prompts (a hardcoded credential or env-var reference flowing into an LLM call's own arguments, distinct from the general Secret Scanner above since the risk is the secret leaving the target's infrastructure to a third-party provider), and missing output validation (an LLM response driving a database query, file path, or shell command with no parse/validate/allowlist check anywhere in the file). Implemented as a lightweight offline ts-morph AST pass (mirrors the Dependency Reachability Scanner's collectCalledPackages pattern), not bundled Semgrep YAML — this codebase's only existing Semgrep rule-file convention is client-authored via the Custom Rule Engine, and a bundled-YAML approach would make this detector's tests depend on the semgrep binary. Findings use the new prompt_injection category for the prompt-injection-surface check and reuse existing categories (broken_access_control, xss, sensitive_data_exposure, and the sink's own category for missing-output-validation) for the other four, since their exploitation mechanics and remediation match those existing categories exactly.
IaC Agent (E16): packages/discovery/src/detectors/iac.ts's detectIac scans Dockerfile/Kubernetes/Terraform infrastructure definitions — a structurally different Layer 1 detector than the app-source SAST engine above, run as its own concurrent fan-out member. Two layers: real, always-on, fully offline structural detectors (packages/discovery/src/detectors/iac/dockerfile.ts, kubernetes.ts, terraform.ts) covering running-as-root containers, ADD-vs-COPY misuse, unpinned/floating base image tags, secrets baked into ENV/ARG layers, a missing .dockerignore risking secret inclusion, Kubernetes missing resource limits, privileged/hostNetwork/hostPID pods, secrets as plain env vars instead of a Secret reference, a repo with no NetworkPolicy anywhere, and Terraform hardcoded credentials, permissive security-group/IAM wildcard rules, and unencrypted storage resources; plus an OPTIONAL Semgrep pass against the real p/dockerfile, p/kubernetes, p/terraform registry packs (reusing sast.ts's parseSemgrepJson/candidateFromSemgrep unmodified) that gracefully degrades — unlike detectSast, this is NOT a required detector. Kubernetes manifests use real YAML parsing (the yaml package) gated on both apiVersion and kind being present, never regex-over-YAML-text; Terraform uses a block-aware, string-literal-safe brace-matching scan (extractResourceBlocks) rather than a full HCL parser, since no HCL parsing library is a dependency of this monorepo. New insecure_configuration Category (packages/contracts/src/compliance.ts, CWE-16, OWASP A05:2021 Security Misconfiguration) covers pure misconfiguration findings that don't already fit hardcoded_secret/broken_access_control/weak_crypto; a matching Prisma migration (state-store/prisma/migrations/8_insecure_configuration_category) mirrors migration 7's prompt_injection precedent exactly.
SBOM Dependency Inventory (E16): packages/discovery/src/sbom.ts's buildDependencyInventory resolves the FULL dependency tree (not just the vulnerable subset detectDependencies emits) plus real call-site reachability (A12) and matched OSV/GHSA advisories, as plain data with zero dependency on @montr/report. packages/report/src/exports/cyclonedx.ts's buildCycloneDxSbom/renderCycloneDxSbom (new "cyclonedx" ExportFormat) structurally consume that exact shape to produce a schema-shaped CycloneDX 1.5 JSON document (real PURLs, per-component montr:reachable properties, vulnerabilities[] with numeric CWEs and affects[] refs) — see that file's module doc for why an SBOM export can't be derived from a Report's confirmedFindings alone, the way every other exporter in that directory is. Proven end to end (discovery's real output piped directly into report's renderer, zero adapter) in tests/sbom.cyclonedx-e2e.test.ts. NOT yet wired to a production route/CLI command that calls buildDependencyInventory and hands it to generateExport — built and fully tested, same "shipped as a library, no production call site yet" posture as several other E-series items (E5's semantic index, E9's escalation); packages/discovery/scripts/check-unwired-seams.mjs does not track this seam (its SEAMS list is curated, not automatic), so this is a documented gap, not a hidden one.
Supply-Chain Risk Agent (E16): packages/discovery/src/detectors/supply-chain.ts's detectSupplyChainRisks runs three checks over SCA's already-resolved dependency set: (1) typosquatting via real Levenshtein edit-distance against a curated ~150-entry popular-npm-package list (levenshtein, detectTyposquats); (2) install-script risk — a preinstall/install/postinstall script in the project's own package.json (always checkable) and, when node_modules is actually present on disk, in a resolved dependency's own node_modules/<pkg>/package.json (detectDependencyInstallScriptRisk reads that ONE specific path directly via FileProvider.read, which has no ignore-list, unlike list()'s walk) — content is pattern-scanned to separate a legitimate build hook from a genuinely suspicious one (remote curl-pipe-to-shell, base64/eval obfuscation, a raw.githubusercontent.com/pastebin.com fetch); (3) basic malicious-package heuristics scoped to what is realistically checkable OFFLINE — non-ASCII/zero-width/bidi-control characters in a package name, and (package-lock.json only) a dependency resolving from a non-standard registry host. All three reuse the existing vulnerable_dependency Category rather than adding a new one (OWASP A06:2021 "Vulnerable and Outdated Components" already covers dependency-sourced risk broadly, not only CVE-tracked vulnerabilities).
Persistence Helper: packages/discovery/src/persist.ts writes CandidateFinding rows to Postgres via packages/state-store.

Output Data and Candidate Normalization
Candidate Finding Entity: Every detected issue is recorded with source tool name, rule identifier, standardized Category enum, CWE list, file path, line number, raw severity, and code evidence snippet.
Golden Rule Guarantee: Candidate findings represent raw input for Layer 2 correlation. They are never displayed as finalized vulnerabilities or used for headline statistics without undergoing correlation and exploit confirmation.

Constraints and Edge Cases
AGENT NOTE: Scanner binaries (Semgrep, gitleaks) execute locally within the worker container environment. In air-gapped deployments, Semgrep runs against a local ruleset directory set via the discovery.rulesetsDir config key (env MONTR_DISCOVERY_RULESETS_DIR), populated by deploy/airgap/build-bundle.sh --semgrep-rules-dir and deploy/airgap/import-bundle.sh (installed under <dest-dir>/semgrep). Unset, SAST is unchanged and uses the hosted Semgrep Registry packs.
AGENT NOTE: SAST is a required detector. detectSast throws RequiredDetectorUnavailableError (packages/contracts/src/errors.ts) instead of degrading to an empty result when Semgrep is missing, errors, or a configured rulesetsDir is missing or has no rule files. The throw propagates through runDiscovery to the Layer 1 orchestrator runner and fails the scan via packages/orchestrator/src/controller.ts failScan, so a scan can never complete successfully with silent zero SAST coverage. Gitleaks and the SCA/dependency detector are unaffected and keep degrading gracefully with a warning.
AGENT AVOID: Never surface raw CandidateFinding counts directly in the UI as confirmed vulnerabilities. Always filter through Layer 2 correlation and Layer 3 confirmation.
AGENT NOTE: SCA call-site reachability (collectCalledPackages, packages/discovery/src/detectors/sca.ts) is TypeScript/JavaScript only and is a same-project AST call-site check, not full interprocedural call-graph reachability from an HTTP entry point — it does not trace through intermediate helper functions. It does NOT reuse packages/appmap/src/languages/typescript/callgraph.ts (scanTaintFlows): that resolver explicitly excludes bare/package specifiers (npm imports) by design, so it cannot answer "was this package's export called" at all. Python/PyPI and JVM/Maven manifests are not yet resolved by this detector; if that changes, their reachability must not silently inherit the TS/JS call-level claim (tracked as A21).
AGENT NOTE: applyThreatModelScopeHints is purely a prioritization/annotation signal, never a filter. Its zeroSurfaceCategories input (categories the threat model rated as having no plausible attack surface, for example xxe on an app with no deserialize-kind taint sink) is deliberately NOT consumed to skip a detector or drop a candidate here — every category still runs unchanged. A future consumer that wants to actually narrow detector execution on a genuine zero-surface case must make that an explicit, separately-reviewed change, not an implicit consequence of this signal.
AGENT NOTE: detectAiSecurity recognizes an LLM SDK call site only when a local variable is constructed via new <Binding>(...) where <Binding> is imported from a known provider package (openai, @anthropic-ai/sdk, @aws-sdk/client-bedrock-runtime, @google-cloud/vertexai, @azure/openai) and the call chain's method suffix matches messages.create/messages.stream/chat.completions.create/completions.create. Like SCA call-site reachability above, this is single-file/same-file analysis only, not interprocedural — a client instance constructed in one file and imported into another is not resolved. Its response-tracking (for the unescaped-output and missing-output-validation checks) is a one-hop-only local dataflow: it follows const html = response.content[0].text but not a value passed through an intermediate helper function. Guard/validation-marker scans strip // and /* */ comments first specifically so a descriptive comment about the vulnerability (or a stale TODO) cannot flip the heuristic.
AGENT NOTE (E16, IaC scope): detectIac's structural detectors are pattern-based, not full-parser-based, for Dockerfile and Terraform (Kubernetes uses real YAML parsing). Dockerfile parsing does not join `RUN a \` + `  && b` line-continuations — checks needing the whole instruction body (USER/FROM/ADD/ENV/ARG) are unaffected since those are single-line in the overwhelming majority of real Dockerfiles, but a continuation-spanning RUN body is not analyzed as one unit. Terraform's extractResourceBlocks resolves real per-resource-block scoping via a string-literal-aware brace counter, but there is no cross-file resolution (an S3 bucket's encryption config living in a different .tf file than the bucket resource is not connected) and no variable/module-graph evaluation (a value behind var.x or a module output is invisible, by design — a false negative, never a false positive, on genuinely uncertain input).
AGENT NOTE (E16, supply-chain scope): detectSupplyChainRisks' malicious-package heuristics are deliberately scoped to offline-checkable signals only — "recently published + low downloads + unusual permissions" (the audit's own suggested heuristic) needs live npm registry metadata this on-prem/BYO-key product does not fetch (golden rule #1: source/dependency data never leaves client infrastructure except to the configured LLM endpoint); this is documented future work, not a silent gap. The dependency-install-script check can only see a resolved package's real node_modules/<pkg>/package.json when node_modules is actually present on disk — true for a CI/post-npm-install scan, never true for a plain git checkout, since node_modules is excluded from fsFileProvider's directory walk by design (util/files.ts's IGNORE_DIRS); this is a true absence of that specific signal for the common case, not a swallowed error, and packages/discovery/src/detectors/supply-chain.test.ts proves the read-one-specific-path mechanism works via an in-memory FileProvider rather than a real (necessarily un-committable, gitignored) node_modules fixture.
