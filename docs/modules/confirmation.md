# Module: Layer 3 Exploit Confirmation and DAST

Scope: Static interprocedural taint proofs, approver-gated live DAST execution, egress guards, and blast-radius controls.
Rendering context: Server
Project tier: 4
Last updated: auto

Overview
The Exploit Confirmation module executes Layer 3 of the analysis pipeline within packages/confirm. It proves whether correlated ProbableFinding records are genuinely exploitable. By default, it performs deterministic static data-flow proofs using high-capacity LLM confirmation models to trace taint paths from source to sink. When explicitly enabled and authorized by an Approver, it conducts live dynamic security testing (DAST) against allowlisted staging targets under strict egress and blast-radius rate limits. When BOTH the static proof and live DAST miss a finding, a third path (agentic investigation, E1/E2/E4 below) may still confirm it, but only after clearing an executable-evidence gate and an adversarial multi-verifier majority — never on a model's opinion alone. As of A3 (2026-09-12) this third path is ON by default in production, scoped to unconfirmed high/critical findings only — see the Production Wiring entry below.

Entry Points and Core Runners
Layer 3 Runner: packages/confirm/src/confirm.ts exports runLayer3Confirm, which evaluates probable findings through static or live proof engines.
Queue Execution: apps/worker/src/runners.ts pulls Layer 3 jobs from BullMQ and executes confirmation against probable findings.

Static Exploit Proof Engine
Static Solver: packages/confirm/src/static.ts uses the confirmation tier model (Claude Opus 4.8) via packages/llm-gateway to construct formal data-flow proofs.
Taint Path Analysis: The engine traces user inputs from Route entrypoints through intermediate variable assignments, function calls, and sanitizers down to dangerous TaintSinks.
Cross-Function Fallback (A21): findSink/findSource in static.ts first look for a same-file taint sink/source (unchanged prior behavior); only when that finds nothing do they now fall back to AppMap.taintFlows — the same interprocedural edge data packages/correlation/src/grounding.ts already reads for Layer 2 scoring — resolving the real TaintSink/TaintSource record by the edge's exact location so assessSink's description-marker heuristics still see the full sink text. This is language-agnostic and purely additive (identical behavior when taintFlows is empty or nothing matches); it is what actually wires the new Python/Java call graphs (packages/appmap/src/languages/{python,java}/callgraph.ts) into Layer 3 confirmation rather than leaving them consumed only by Layer 2 grounding, which was previously the ONLY consumer of taintFlows even for TypeScript.
Static Proof Artifact: Generates a structured ProofArtifact object detailing the exact source-to-sink variable path and sanitization gaps.

Live DAST Engine and Safety Guards
Live Prober: packages/confirm/src/live.ts executes targeted HTTP requests against deployed staging web applications to confirm exploitability.
DAST Guard: packages/confirm/src/guard.ts enforces non-negotiable safety policies:
Allowlist Enforcement: Probes are permitted exclusively against URLs registered in the DastTarget table.
Production Blocking: Production environments are blocked unconditionally by policy.
Approver Authorization: Live runs require explicit Approver role approval on POST /api/v1/scans/:id/dast/authorize.
Scope Contract Limits: Enforces strict caps on maximum total requests, concurrency limits, requests per second, and max mutating operations. The mutating-request cap defaults to zero, so any POST-based probe (XXE, insecure deserialization) is refused by policy unless an operator explicitly raises it.
Network Egress Guard: All outbound HTTP requests route through packages/security/src/egress-guard.ts, which blocks connections to non-allowlisted network addresses.
Scenario Runner: packages/confirm/src/scenarios.ts decrypts and executes versioned multi-step RedTeamScenario playbooks. Its runScenario function is transport-agnostic: called with no transport (apps/api/src/routes/scenarios.ts's POST /scenarios/:id/run) it only authorizes and gate-checks every step in-process and nothing ever leaves the process; called WITH a real transport (apps/worker/src/scenario-runs, and Layer 3's own purple-team loop below) it actually probes. See the Standalone Red-Team Scenario Execution section below for the worker-side path and its written-authorization gate.

Live-Confirmable Categories and Probe Coverage
LIVE_CONFIRMABLE_CATEGORIES in packages/confirm/src/live.ts lists eleven categories with a safe, high-signal live oracle: sql_injection, nosql_injection, xss, open_redirect, ssrf, idor, broken_access_control, path_traversal, command_injection, xxe, and insecure_deserialization. craftProbes emits a baseline request plus a category-specific payload for each; the oracle function applies a fixed marker/status heuristic per category (error-string leaks for injection categories, cloud-metadata markers for ssrf, denial-marker absence plus a differing body for idor, a stripped-credentials request that still succeeds for broken_access_control, POSIX /etc/passwd disclosure markers for path_traversal and xxe, marker reflection for command_injection, and deserializer-error/type-echo markers for insecure_deserialization). nosql_injection sends a real Mongo/NoSQL bracket-notation operator payload (field[$ne]=value) rather than a SQL string. idor and broken_access_control have no static data-flow proof at all (absent from DATAFLOW_SINK_KINDS in packages/confirm/src/taxonomy.ts), so live DAST is currently the only path that can ever confirm them.
AGENT NOTE: xxe and insecure_deserialization are POST-based (their sinks only trigger on a parsed request body); the insecure_deserialization payload is a malformed/typed object that only ever proves the sink parses attacker-controlled data via an error or type-name echo — it never sends an executable gadget chain.

Adaptive Exploit Agent (E3)
The fixed craftProbes/oracle single-payload path above always runs FIRST for every live-eligible finding — fast, zero LLM cost, and it resolves the large majority of probes cleanly (a clean hit or a clean miss). Only when that fixed attempt's verdict is AMBIGUOUS does packages/confirm/src/live.ts's runAdaptiveLoop engage: isAmbiguous flags a response suggesting the payload reached something real without tripping the fixed oracle — a raw 5xx on the payload attempt, a generic error/stack-trace leak (injection categories), a filter-block signal or 400/403 (ssrf), a redirect that fired but didn't match the exact off-site target (open_redirect), or a reflected-but-transformed fragment (xss). On ambiguity the loop asks deps.llm (confirmation tier, low effort, resolvePrompt name confirm.live_adaptive.system) to pick ONE variant id from a small, hardcoded, per-category PAYLOAD_VARIANTS catalog — recognizable exploit-technique mutations (alternate SQL comment styles and a UNION column probe; NoSQL $gt/$regex/$exists operators; decimal/IPv6-mapped/alt-hostname SSRF encodings; attribute-breakout/<img>/<svg> XSS vectors; protocol-relative/backslash/userinfo-@ open-redirect bypasses; encoded/double-encoded/null-byte path-traversal variants; pipe/backtick/$() command-injection forms; alternate XXE target files/parameter-entity indirection; alternate deserialization type markers; IDOR id and header-stripping variants for broken_access_control) — never a free-form model-authored payload; responseSchema constrains the reply to the exact enum of offered ids, and the caller re-validates the returned id against that same set before ever building a request from it. Every adaptive probe passes through the SAME ScopeGuard.assertProbeAllowed gate as every fixed probe (allowlist, production block, kill switch, rate/blast-radius caps, egress guard) — nothing bypasses guard.ts. The loop is capped at MAX_ADAPTIVE_ROUNDS = 3, a hard ceiling INDEPENDENT of the gateway's own A2 pre-call budget guard (defense in depth). The kill switch is re-checked via guard.assertNotKilled() at the top of every round AND immediately after every LLM call returns (not just once at the start), so an activation mid-investigation halts probing before the next request ever leaves the process; a BudgetExceededError or any other gateway failure during variant selection is caught and stops the loop fail-safe, keeping whatever verdict/transcript already exists. oracle() now scores against the MOST RECENT payload/adaptive_payload-role probe (a reverse-find, not the first), so a later adaptive round correctly supersedes the fixed payload for verdict purposes — a no-op on the fixed-only path, which only ever produces one payload entry.
AGENT NOTE: the adaptive loop only engages when deps.llm is supplied AND the fixed attempt was ambiguous — every fixed-path test (none of which pass an llm) is unaffected; tests/confirm.live.test.ts asserts zero extra gateway calls on clean-hit and clean-miss cases as the regression guard.

Agentic Investigation Loop, Executable-Evidence Gate, and Adversarial Confirmation (E1, E2, E4)
Investigation Loop (E1): packages/confirm/src/investigate.ts's runInvestigation gives the confirmation-tier model a multi-turn, tool-calling loop over packages/confirm/src/investigate-tools.ts's seven READ-ONLY tools — read_file, grep, find_definition, query_call_graph, semantic_search, list_routes, get_orm_model — plus a terminal submit_conclusion tool. It runs ONLY when a probable finding cleared neither the deterministic static proof nor live DAST, and only when ConfirmDeps.investigation.enabled is true — the interface itself still defaults this to falsy for a caller building ConfirmDeps directly (every existing offline test is unaffected), but as of A3 (2026-09-12) the production Layer 3 runner populates it from config.confirmation.investigation, which defaults enabled to TRUE (see the Production Wiring entry below) since this is a materially larger cost/latency profile per finding than the existing single-call static veto. read_file/grep/find_definition read the scan's repo checkout at ConfirmInput.repoRoot when one is supplied (not yet wired from apps/worker/src/runners.ts — documented, narrow follow-up, matching this codebase's established built-and-tested-but-not-yet-wired pattern); list_routes/get_orm_model/query_call_graph always work, reading only the already-built AppMap. semantic_search (A9) retrieves code by MEANING rather than literal text via packages/semantic-index's querySemanticIndex, injected as ConfirmDeps.semanticSearch and wired to a real callback in apps/worker/src/runners.ts's layer3 runner whenever the semantic codebase index is enabled and available; absent that, the tool degrades to an honest "no semantic code index available" result rather than throwing, mirroring read_file/grep's no-repo-checkout degradation. This is what gives IDOR and broken_access_control (previously 0% recall, absent from DATAFLOW_SINK_KINDS with no static proof at all) a real path to confirmation beyond live DAST alone. A hard structural ceiling of 8 tool-call turns (ABSOLUTE_MAX_INVESTIGATION_TURNS in investigate.ts) is enforced regardless of any config override, independent of and additive to the A2 pre-call budget guard on every individual gateway call; exhausting the turn budget always yields verdict "inconclusive", never "confirmed_candidate" (fail-safe).
Live Progress Narration (E10): the loop is the first real producer for packages/orchestrator's LayerRunContext.emitProgress(phase, pct, message) (see docs/modules/orchestration.md and docs/modules/llm-gateway.md's Streaming entry, both previously documenting it as built-but-unwired). ConfirmDeps gained an additive, optional emitProgress?: (phase, pct, message?) => void field (packages/confirm/src/types.ts), threaded straight from apps/worker/src/runners.ts's layer3 runner as emitProgress: ctx.emitProgress — the identical pass-through pattern signal/logger already use. investigate.ts's runInvestigation calls it exactly once per investigation turn with phase "investigating", a pct estimated from turn/turnsCap, and a message derived from the ACTUAL tool call that turn made (e.g. "Reading app/api/orders/[id]/route.ts...", "Checking the call graph for ...", "Submitting investigation verdict (confirmed_candidate)..." — never a generic placeholder); the callback is invoked in a try/catch so a broken consumer can never break the investigation. Purely additive: omitting emitProgress (the default in every existing test and any caller that doesn't set it) leaves the loop's outcome byte-identical to before this change. apps/web/src/components/layer-progress.tsx already renders this phase/pct live — no console changes were needed.
Executable-Evidence Gate (E2): a "confirmed_candidate" verdict from the investigation loop is a PROPOSAL, never a promotion. packages/confirm/src/evidence.ts's gatherExecutableEvidence requires the investigator to have named a real, pre-existing test file (found via its own read-only tools, never invented) that FAILS when actually executed — via a real, bounded (default 15s timeout) subprocess run of that ONE file through the target repo's own vitest binary (node:child_process execFile, no shell interpolation). A named test that passes, that cannot be launched, or that was never named at all all count as "no evidence", and the candidate goes no further. A live-DAST evidence route is also named in the design (reusing the SAME live.ts probe already attempted earlier for that finding) but no independent second live attempt is implemented in this change — documented scope decision, see investigation-pipeline.ts.
Adversarial Confirmation Panel (E4): packages/confirm/src/adversarial.ts's runAdversarialVerification wraps a candidate that cleared E2 in up to four independent, sequential verifier calls with distinct lenses — exploitability, reachability, business_impact, and an explicitly adversarial refutation pass that is shown the other three verdicts and instructed to actively try to disprove the finding. A STRICT MAJORITY (3 of 4 by default; floor(N/2)+1 for any configured N) must vote confirm or the candidate is not promoted; a verifier call that errors or returns unparseable output counts as a reject vote, never a silent confirm. packages/confirm/src/investigation-pipeline.ts's attemptInvestigationConfirmation is the sole integration point tying E1→E2→E4 together and is called from confirm.ts ONLY as the last resort after both the static and live paths miss; a finding it confirms gets a "static"-kind ProofArtifact (no new proof-artifact kind was added to packages/contracts for this task) whose argument embeds the investigator's rationale, the evidence summary, and the full per-lens verifier tally.
A17 bug fix (2026-09-12): runOneVerifier's request now sets an explicit request.responseSchema matching its own {confirm, rationale} reply shape (see packages/confirm/src/adversarial.test.ts). It previously relied on metadata.purpose: "confirmation" alone, which packages/llm-gateway/src/structured-output.ts's purpose-keyed map resolves to static.ts's DIFFERENT {confirmed, argument} schema — under real provider-side schema-constrained decoding this would have silently forced every real verifier reply into the wrong shape (additionalProperties:false strips confirm/rationale entirely), so every verifier would read as an undefined vote and always reject. This was invisible to every existing test because none exercise real schema enforcement (all mock LLMGateway.complete() directly). At the time this bug was fixed, no pipeline caller invoked this path in production (see the A3 entry below), so it had no live customer impact then — but as of A3 landing, E4 is genuinely reachable in production, so this fix is now load-bearing rather than latent.
AGENT NOTE: the hard invariant across all three enhancements — a model's unverified opinion NEVER confirms a finding by itself. E1's "confirmed_candidate" alone does nothing; it must also clear E2's real executable-evidence gate AND E4's adversarial majority before packages/confirm/src/confirm.ts ever pushes it onto the confirmed array.

Structural Scoping Gate and Proportional Effort Allocation (A11, 2026-09-12 red/blue agentic-posture audit)
packages/confirm/src/structural-gate.ts's structuralConfirmationGate runs in confirm.ts's per-finding loop immediately after the existing §15 false-positive check and before any static proof, live DAST, or agentic investigation work begins. It is a bounded, deterministic existence check, never a score or threshold judgment: when a probable finding carries a routeId, it verifies that route still appears in the exact App Map Layer 3 is confirming against. Layer 2's own grounding (packages/correlation/src/grounding.ts) already demotes every candidate it cannot corroborate before it is ever promoted to probable, so within one continuous scan this can never fire — it only protects a resumed/distributed scan whose App Map was rebuilt (AppMap.stale/rebuildPolicy, packages/contracts/src/appmap.ts) between correlation and confirmation, where a finding's registered route can have genuinely disappeared. A finding with no routeId (off-route: secrets, vulnerable dependencies, non-route entrypoints) is always left untouched, since those categories are legitimately corroborated by Layer 2 through a different structural surface and are not indexed by file the way routes are. A ruled-out finding is routed straight to the Unconfirmed appendix via toUnconfirmed with an explicit "structurally ruled out" reason string and a finding.demoted audit event (metadata.reason: "structurally_ruled_out") — never silently dropped.
packages/confirm/src/investigation-pipeline.ts's attemptInvestigationConfirmation additionally scales the investigation loop's turn budget (ConfirmDeps.investigation.maxTurns, exported as investigate.ts's DEFAULT_MAX_TURNS) per finding, using the same reachabilityScore × exposureScore × impactScore product Layer 2 already ranks findings by (no new scoring signal introduced): a finding scoring 0.5 or higher gets the caller's full configured turn budget, a finding scoring below 0.15 gets roughly half, everything else gets three-quarters, with a floor of 2 turns. This can only scale the configured budget DOWN relative to the caller's own setting, never up, and the result remains subject to investigate.ts's unconditional ABSOLUTE_MAX_INVESTIGATION_TURNS ceiling regardless of what the scaling computes. Live DAST's adaptive-round cap (live.ts's MAX_ADAPTIVE_ROUNDS) was deliberately left unscaled in this change — it is a module-level constant threaded through a much larger call path, and scaling it carried disproportionate risk relative to this audit item's scope; a future pass can extend the same score-driven allocation to it.

Production Wiring, Severity Scoping, and Budget Coverage (A3, 2026-09-12 red/blue agentic-posture audit)
The E1/E2/E4 agentic investigation loop above was previously reachable only by a test/caller manually constructing ConfirmDeps.investigation — no config field existed and no production caller populated it. packages/config/src/schema.ts now carries ConfirmationInvestigationConfigSchema under confirmation.investigation: enabled (owner decision — defaults to TRUE, a deliberate deviation from every other agentic-loop toggle in this codebase, all OFF by default, because idor/broken_access_control have zero static data-flow proof and this is the only static-scan path that can ever confirm them), maxTurns (default 6, capped at 8 to match investigate.ts's own unconditional hard ceiling — config cannot raise it past what the code already enforces), verifierCount (default 4, capped at 4 to match adversarial.ts's 4-lens panel), and severities (default high and critical — the owner's scoping decision). apps/worker/src/runners.ts's Layer 3 runner populates ConfirmDeps.investigation straight from this config, mirroring the A5 fixGeneration.agentLoop wiring convention exactly.
Severity Scoping: ProbableFinding carries no severity field at all (severity is assigned only at confirmation, on ConfirmedFinding). packages/confirm/src/confirm.ts's isEligibleForInvestigation computes a not-yet-confirmed finding's eligibility via baseSeverityForCategory(category) in taxonomy.ts — the category's class severity — and checks it against ConfirmDeps.investigation.severities before ever calling attemptInvestigationConfirmation. An ineligible finding (i.e. a category whose base severity is outside high/critical under the production default) never reaches the investigation loop at all — this is a real cost gate, not merely an outcome filter, so ineligible findings spend zero extra LLM budget. AGENT NOTE: this deliberately does NOT use deriveSeverity(category, exposure) — the exposure-discounted function that sets a _confirmed_ finding's final severity — because idor and broken_access_control both have a "high" base severity and the overwhelmingly common real-world instance of either is authenticated-only, not anonymous-public; gating eligibility on the discounted value would have silently excluded that common case from the default scope, defeating the reason this loop exists. A finding's final reported severity is still computed correctly via deriveSeverity at confirmation time, unaffected by this gate.
Budget Coverage: no new wiring was needed — every investigation-loop and E4 adversarial-verifier LLM call already carries the scan's real metadata.scanId and is dispatched through the SAME LLMGateway instance every other Layer 3 call uses, so the existing A2 pre-call budget guard (packages/llm-gateway/src/gateway.ts's assertPreCallBudget, keyed off packages/orchestrator/src/controller.ts's per-scan budgetRegistry.register) already enforces MONTR_BUDGET_MAX_USD / MONTR_BUDGET_MAX_TOKENS / MONTR_BUDGET_ENFORCEMENT=hard_halt against this spend unchanged.
AGENT NOTE: this is a real behavior and cost change for every operator upgrading — see docs/overview.md's Recent Changes entry and docs/infra/environment.md.

Purple-Team Verification Loop (B5)
packages/confirm/src/purple-loop.ts is the purple-team differentiator: it runs a RedTeamScenario through the identical gated scenarios.ts runScenario entry point (no new execution path — the exact same assertScenarioAuthorized plus ScopeGuard gate: kill switch, allowlist, production block, blast-radius and rate caps, egress guard) and then structurally checks whether a B3-generated Sigma DetectionRule for the same confirmed finding would actually have fired against the resulting transcript. parseSigmaRule parses only the fixed shapes packages/report/src/detection-rules/sigma.ts's buildSigmaRule ever emits (route-based cs-uri-stem|startswith / cs-method / cs-uri-query|contains / cs-body|contains selections joined by "and"/"1 of", or the file-fallback TargetFilename|contains selection) into a structured spec; evaluateSigmaRule evaluates that spec against a request's method, URL, and body — a real, faithful subset evaluator for exactly what B3 produces, not a generic Sigma engine, and never a coin flip. evaluateDetectionRuleAgainstScenario runs this across every exchange in a scenario's real transcript, reporting the firing exchange when one fires or the most informative near-miss (with a concrete, non-generic reason) when none does.
AGENT NOTE (A10, 2026-09-12): RedTeamStep (packages/contracts/src/phase4.ts) now carries an optional request-body field. runScenario's transport.send call sends it verbatim when a step defines one and records it on the transcript exchange, so a rule whose condition depends on cs-body|contains CAN fire against a scenario-run transcript — this closes what was previously a genuine, universal structural gap. The gap is now per-step, not per-product: a step that defines no body still evaluates with no body content, and evaluateSigmaRule still names this explicitly in its reason text rather than silently returning fired: false. The three OWASP starter-catalogue scenarios whose confirming payload is a POST body (command_injection, insecure_deserialization, ssrf in packages/state-store/src/redteam-catalogue.ts) now populate this field on their confirming step and fire correctly, confirmed by packages/qa/src/blue-team-corpus.ts's real measured run (see docs/infra/testing.md).
runPurpleTeamScenario ties the gated run and the evaluation together and returns a DetectionVerificationResult; verifyScenarioDetection additionally finds-or-creates the finding's DetectionCoverage row (read-only consumption of the B1 repository, packages/state-store/src/blue-team.ts) and persists the verdict via DetectionCoverageRepository.updateVerification. summarizePurpleTeamRun is a pure, standalone report-summary builder (scenario, finding, detected/undetected, why).

NOW WIRED (A8): apps/worker/src/runners.ts's Layer 3 runner calls this loop, not Layer 5 — it needs the SAME approver-gated live-DAST authorization (Layer3JobData.allowLive/stagingUrl) Layer 3's own live confirmation path already uses, and Layer5JobData carries no such field. Scoped to run only when allowLive is true (a scenario run with no authorization only ever produces an empty transcript, which would misleadingly read as a real detection gap rather than "never attempted"). Scenario selection is category-based, mirroring packages/qa/src/blue-team-corpus.ts's own hand-traced pattern: for each confirmed finding, the worker looks up this client's real, ENABLED RedTeamScenario catalogue rows (StateStore.redTeamScenarios.list) and picks the first one whose coarse RedTeamCategory maps (via the exported REDTEAM_CATEGORY_TO_FINDING_CATEGORIES) to the finding's category; no match is skipped, never assigned an arbitrary scenario. Candidate DetectionRules for the evaluation are generated in-memory via packages/report/src/detection-rules/generate.ts's generateDetectionRules (the same pure generator report-builder.ts calls at Layer 5), never persisted by this call. The transport is packages/confirm/src/live.ts's own defaultTransport (now exported), reused verbatim — no second HTTP client, no new egress path. Every (finding, scenario) pair is attempted independently and best-effort: a guardrail refusal (off-allowlist, dast.enabled=false, production-looking target) or any other error is logged and skipped, never aborts Layer 3's confirmed/unconfirmed output. The resulting summarizePurpleTeamRun(...).entries travel to Layer 5 ONLY through the orchestrator's in-process priorOutputs cache (Layer3Output gained an additive, non-persisted purpleTeamEntries field, packages/contracts/src/layers.ts — mirrors Layer2Output.demoted's identical non-persisted-cache-only precedent) and are threaded into BuildReportInput.purpleTeamEntries; `[]` on a resumed/distributed run where the cache is empty, never a fabricated verdict.

Standalone Red-Team Scenario Execution and Written Authorization (A1, 2026-09-12 red/blue agentic-posture audit)
Before A1, POST /scenarios/:id/run always called runScenario with an empty deps object — no transport — so a "run" only ever authorized and gate-checked every step; nothing was ever actually probed anywhere, despite the operator console previously implying otherwise. This is now closed with a genuine worker-side execution path, deliberately kept SEPARATE from Layer 3's own purple-team loop above (which verifies detection coverage for a confirmed finding as part of a scan): apps/worker/src/scenario-runs is a standalone, on-demand action triggered directly from POST /scenarios/:id/run, not a step in the six-layer pipeline.
Queueing: a dedicated, non-pipeline BullMQ queue (packages/contracts/src/queue.ts's SCENARIO_RUN_QUEUE_NAME, separate from the per-layer FSM queues) carries one ScenarioRunJob (scenarioId, clientId, requestedById, requestedAt) per authorized run request. apps/api/src/scenario-run-producer.ts enqueues (produce-only, mirrors apps/api/src/enqueue-scheduler.ts's produce-only role for the pipeline queues); apps/worker/src/scenario-runs/bullmq-transport.ts consumes, both lazily loading bullmq/ioredis exactly like apps/worker/src/scheduling/bullmq-transport.ts's established convention.
The Written-Authorization Gate: apps/worker/src/scenario-runs/service.ts's processScenarioRunJob re-loads the scenario record (never trusts the job payload alone), re-checks every pre-existing safety gate (scenario.enabled, config.dast.productionBlocked/killSwitchEnabled invariants), and adds ONE new gate BEFORE any transport is ever constructed: packages/contracts/src/phase4.ts's hasLiveRunAuthorization must be true. This requires an Approver to have separately called POST /scenarios/:id/authorize with a non-empty authorizationReference (a ticket number or signed agreement reference — genuinely more than "an Approver clicked a button"), bound to the scenario's exact current version — see docs/auth/authorization.md and docs/api/database.md for the persisted fields. Missing or stale (edited-since-authorized) authorization is a fail-closed rejection, audited as scenario.live_run_rejected, and never constructs a transport. Real execution reuses packages/confirm/src/live.ts's exported defaultTransport — the SAME real HTTP transport Layer 3's own live confirmation and the purple-team loop above already use — no new egress path, and it always runs against the scenario's own authorized targetAllowlistRef, never an ad hoc override. A successful run is audited as scenario.live_run_executed. processScenarioRunJob never throws — any unexpected failure (store, transport, or guardrail) is caught, logged, and reported as a rejected outcome, so a bad job can never crash the BullMQ consumer loop.
AGENT NOTE: this gate is strictly additive on top of every existing DAST safety control (production blocking, packages/confirm/src/guard.ts's ScopeGuard allowlist/rate/blast-radius/egress checks, the kill switch) — none of them were weakened to add it.

Confirmed Finding Persistence
Confirmed Finding Entity: Successfully validated vulnerabilities are persisted as ConfirmedFinding rows in Postgres with attached ProofArtifact (static or live), severity classification, CWE identifiers, and OWASP tags.
Executable-Evidence Promotion: packages/confirm/src/static.ts's LLM cross-check can only demote a statically-reachable finding to the Unconfirmed appendix — it has no branch that reads confirmed === true from a model verdict. Two paths promote a finding on evidence rather than a model's bare word: a successful live-DAST probe (packages/confirm/src/live.ts's confirmLive, wired in packages/confirm/src/confirm.ts — a real HTTP request/response transcript proving exploitability, attached as the finding's live ProofArtifact), and, as of E1/E2/E4 above, the agentic investigation path once it clears BOTH the executable-evidence gate and the adversarial majority.

Constraints and Edge Cases
AGENT NOTE: DAST is disabled by default. When enabled, live probing can be aborted instantly across all nodes by triggering the emergency kill switch.
AGENT AVOID: Never bypass allowlist checks or blast-radius rate limits in packages/confirm/src/guard.ts under any circumstances.
