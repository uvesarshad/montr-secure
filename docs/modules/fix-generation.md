# Module: Layer 4 Fix Generation and Risk Classification

Scope: Automated patch synthesis, proof-of-fix regression test generation, and safety risk classification.
Rendering context: Server
Project tier: 4
Last updated: auto

Overview
The Fix Generation module executes Layer 4 of the analysis pipeline within packages/fix. For every ConfirmedFinding identified in Layer 3, it synthesizes a minimal unified diff patch and a companion proof-of-fix regression test. The module applies a safety risk classifier to categorize each remediation as either auto-eligible or human-required. Remediations touching sensitive security domains are strictly classified as human-required, guaranteeing that critical application logic is never modified without engineer oversight.

Entry Points and Core Runners
Layer 4 Runner: packages/fix/src/generate.ts exports generateFixes, which iterates over confirmed findings to produce patches, regression tests, and safety classifications.
Queue Execution: apps/worker/src/runners.ts pulls Layer 4 jobs from BullMQ and executes fix synthesis for confirmed findings.

Key Components and Fix Strategies
LLM Fix Proposal: packages/fix/src/generate.ts asks the default tier model (Claude Sonnet 5) via packages/llm-gateway to propose a fix as a targeted, line-anchored edit list rather than a full-file rewrite (see LLM Fix Proposal Format below), then reconstructs the fixed source and hands it to the patch builder.
Patch Builder and Validator: packages/fix/src/patch.ts builds the unified diff from the original and reconstructed fixed source and validates it by actually executing the generated proof-of-fix test through a real vitest subprocess, once pre-patch and once post-patch. See Real Ephemeral-Container Proof-of-Fix (E13) below for the strict, opt-in upgrade over this mechanism.
Strategy Registry: packages/fix/src/strategies.ts provides category-specific remediation strategies including parameterized database queries for SQL injection, context-aware output encoding for XSS, strict URL parsing for SSRF, and manifest updates for vulnerable dependencies.
Proof-of-Fix Test Generator: packages/fix/src/generate.ts synthesizes automated regression test cases designed to fail against unpatched code and pass once the patch is applied.
Risk Classifier: packages/fix/src/risk.ts evaluates modified AST nodes and finding categories to assign a RiskClass (auto-eligible or human-required) with an explanatory rationale.

LLM Fix Proposal Format
Line-Anchored Edits: The model receives the vulnerable file with every line prefixed by its 1-based line number and returns a small JSON edit list, each entry a 1-based inclusive startLine/endLine range plus a replacement block, instead of the previous whole-file-rewrite contract. packages/fix/src/edits.ts parses, validates (rejects out-of-range, malformed, or overlapping ranges), and applies these edits to the original source before it flows into the existing patch builder unchanged.
AGENT NOTE: This closed audit finding A14. The prior contract asked for the entire fixed file back, which truncated and failed JSON parsing on any file past roughly 1,500 lines with no error or metric. Scoping the response to only the changed lines removes that ceiling.
Output Budget: The fix-generation call's token cap is 8192, four times the prior whole-file-rewrite cap, sized for several edit hunks of real code rather than an entire file.
Failure Visibility: An unparseable model response or a structurally invalid edit list is recorded via packages/telemetry's getMetrics().recordError with codes fix_generation.llm_response_unparseable and fix_generation.llm_edits_invalid respectively, and logged with the model id and stop reason (flagging a likely truncation when stopReason is max_tokens), so a fleet-wide collapse in LLM-proposed fix quality is observable rather than a silent, uncounted degrade to the mechanical strategy or advisory path. A deliberate model decline (an empty JSON object) is not treated as a failure and is not counted.

Bounded Agentic Fix Loop (A5)
AGENT NOTE: This closed audit finding A5 (depends on A4's gateway tool-call round-tripping in packages/llm-gateway/src/mapping.ts and packages/contracts/src/llm.ts's LLMMessageSchema.toolCalls). packages/fix/src/generate.ts's FixGenerationContext.agentLoop is OFF by default, mirroring the containerProof/investigation.enabled constructor-opt-in convention used elsewhere in this module and packages/confirm. When absent or disabled, fix generation is the exact single-shot LLM Fix Proposal Format described above, unchanged.
What Enabling It Does: with agentLoop.enabled set, generate.ts's proposeFixWithAgent replaces the single gateway call with a bounded loop, up to agentLoop.maxIterations real proposal attempts: propose an edit list, check it, feed back a specific failure reason, retry. Setting agentLoop.maxToolCalls above zero additionally exposes a sandboxed read_file tool (backed by the same FixGenerationContext.source reader every other read in this module uses, never raw filesystem access) so the model may inspect imported or sibling files before answering; tool round-trips are bounded separately from proposal attempts and never consume an iteration.
Why The Loop's Oracle Stays Cheap: patch.ts's validatePatch spawns a real vitest subprocess (seconds each), and container-validate.ts's validatePatchWithContainerReplay can additionally build a real Docker container per call. Running either of those once per retry would turn a bounded few-iteration loop into a multi-second-per-iteration one. So the loop's own retry/feedback cycle is driven ONLY by a cheap, in-process check (build the unified diff, apply it with the diff library, and test the target strategy's own vulnerability regex predicate against the result) — no subprocess, no Docker, inside the loop. The real vitest-subprocess (and, when containerProof is also enabled, container-replay) verification still runs exactly once per final candidate in generateOne, completely unchanged from the single-shot path.
Feedback Reconciled With edits.ts: a retry's feedback message names the actual problem — a not-valid-JSON reply, a structurally invalid edit list (out-of-range, malformed, or overlapping ranges, per edits.ts's own parseLlmEdits rejection reasons), the vulnerable pattern not detected in the original file, or the vulnerable pattern still present after the proposed edit — never a generic "try again".
Audit Visibility: the fix.generated audit event's metadata gains an iterations field (the number of real proposal attempts taken; 1 for the unchanged single-shot path) — a round-trip count, metadata only, never a code body.
Wired to Production via Configuration (closes the "enable A5 in production" decision): apps/worker/src/runners.ts's Layer 4 runner reads ctx.config.fixGeneration.agentLoop and populates FixGenerationContext.agentLoop ONLY when the operator has set fixGeneration.agentLoop.enabled to true — otherwise the field is left absent (not `{enabled: false}`) so generate.ts's `ctx.agentLoop?.enabled` branch takes the exact single-shot path, byte-for-byte the same request as before this wiring existed. This is a configuration-only switch: no code change or rebuild is required to turn it on for a given deployment.
Configuration: packages/config/src/schema.ts's FixAgentLoopConfigSchema adds a fixGeneration.agentLoop section to MontrConfig — enabled (boolean, default false), maxIterations (non-negative integer, default 3, capped at 10), and maxToolCalls (non-negative integer, default 0 — no tool exposed — capped at 20). The caps exist so a config typo (an extra zero) cannot turn into runaway spend. packages/config/src/loader.ts's envOverlay maps MONTR_FIX_AGENT_LOOP_ENABLED, MONTR_FIX_AGENT_LOOP_MAX_ITERATIONS, and MONTR_FIX_AGENT_LOOP_MAX_TOOL_CALLS onto it, following the same env-var convention as every other opt-in feature in that file (e.g. MONTR_QUEUE_PER_TENANT_ISOLATION).
Cost and Latency Implications (operator decision, not a default): enabling this raises both cost and latency per fix. Each retry the loop takes is another full model round-trip on top of the single-shot call's one; maxToolCalls above zero adds further round-trips for read_file tool use. A deployment that sets maxIterations: 3, maxToolCalls: 2 can therefore spend up to 5 gateway calls per confirmed finding where the default path spends exactly 1. This is a deliberate operator tradeoff (more agentic, multi-file-aware fixes vs. more tokens and wall-clock time per finding) and stays OFF unless explicitly configured.

Safety Classification Rules
Auto-Eligible Classification: Assigned only to low-risk, self-contained modifications such as missing security response headers, strict cookie attributes, and simple dependency version bumps in package manifests.
Human-Required Classification: Hard rule enforced across all fixes touching authentication mechanisms, session management, cryptographic operations, access control, IDOR, or CSRF protections. These categories are permanently barred from automated merging.

Real Ephemeral-Container Proof-of-Fix (E13, closes A22)
AGENT NOTE: This closed audit finding A22. patch.ts's vitest-subprocess mechanism above is genuinely real execution, but its generated test body was a filesystem read plus expect(source).not.toMatch(vulnerable) — it proved the vulnerable PATTERN was gone from the file, not that the application is secure at RUNTIME.
Strict, Additive Upgrade: packages/fix/src/container-validate.ts's validatePatchWithContainerReplay wraps validatePatch with the SAME PatchValidation shape plus an additive containerReplay evidence block (ContainerPatchValidation). It never removes vitest-subprocess coverage — it only adds a stronger proof path on top of it, gated by FixGenerationContext.containerProof (OFF by default, mirrors the ConfirmDeps.investigation.enabled / escalation constructor-opt-in convention used elsewhere in this codebase).
Container Harness: packages/fix/src/container-harness.ts's startEphemeralContainer builds and runs a genuinely throwaway Docker container for a target application checkout. Genericity, stated honestly: a target with its own Dockerfile is built as-is; a target with a package.json "start" or "dev" script but no Dockerfile gets a minimal synthesized node:20-alpine Dockerfile; anything else (no Dockerfile, no recognizable Node entry point — a source-only Python or JVM checkout, for example) is out of scope for this pass and fails closed with a clear error rather than guessing.
Network Isolation: the container is attached only to a freshly-created, dedicated bridge network with IP masquerade explicitly disabled (docker network create --opt com.docker.network.bridge.enable_ip_masquerade=false). Verified empirically against a real Docker engine: with masquerade off, the container's own outbound connections (to the real internet, or to any other container/network on the host) fail closed, while inbound connections via a loopback-only published port (-p 127.0.0.1:0:<port>) still work. A plain --internal network was tried first and rejected — on real Docker engines that flag disables the same NAT chain published-port forwarding depends on, so -p stops working entirely; masquerade-disabled is the mechanism that actually keeps inbound reachable while blocking outbound, mirroring packages/confirm/src/guard.ts's "no unscoped egress" discipline at the network layer instead of the HTTP layer.
Bounded and Fail-Closed: every docker invocation (network create, build, run, port lookup, teardown) shares one timeout budget; a container that fails to build, start, or become ready within it throws, which validatePatchWithContainerReplay catches and degrades to the vitest-subprocess mechanism rather than hanging the pipeline. Teardown always removes the container and the network, both on success and on any failure path.
Exploit Replay: packages/fix/src/exploit-replay.ts reuses the CONFIRMED finding's own live-DAST proof artifact (ConfirmedFinding.proofArtifact of kind "live", produced by packages/confirm/src/live.ts) — read-only; this module does not import or duplicate live.ts's probe-crafting/oracle logic, it only replays the already-captured HttpExchange transcript. pickReplayExchange takes the transcript's LAST entry (the fixed-path payload, or the most recent adaptive-round payload — the same entry confirmation.md documents live.ts's own oracle as scoring against), rewriteRequestForContainer re-targets it at the container's base URL, and exploitEvidenceMatches judges success by comparing the replayed response against the ORIGINALLY recorded evidence (a shared long substring of the response body, or an exact status-code match when the original evidence carried no usable body) — a real, generic comparison against actual recorded evidence, not a fixed per-category regex.
Two-Phase Proof: for a container-eligible finding, validatePatchWithContainerReplay builds one ephemeral container from the pre-patch source and asserts the replayed probe reproduces the recorded exploit evidence, then builds a second ephemeral container from the post-patch source and asserts the SAME probe no longer does. failsPrePatch/passesPostPatch are derived from this real runtime outcome instead of a regex when container replay succeeds end to end.
Fallback (requirement, not a gap): a finding with no live-DAST proof artifact (static-proof-only or E1/E2/E4 investigation-path confirmations), an empty transcript, or no targetRepoDir supplied always falls back to the existing vitest-subprocess validatePatch unchanged — this is a strict upgrade path, coverage for non-live-evidence findings is never broken. A genuine container-infrastructure failure (docker unavailable, build/start error, readiness timeout) also degrades to the vitest mechanism, but with containerReplay.error populated so the degrade is visible, never silent.
Evidence Placement (golden rule #1): the FULL replay evidence (harness kind, per-phase outcome, and the real request/response transcript for both runs) is persisted on Fix.proofOfFixTest.containerReplay (packages/contracts/src/fix.ts's additive ContainerReplayEvidenceSchema, reusing findings.ts's HttpExchangeSchema) — never on the fix.generated audit event, which gets only a LEAN summary (attempted/replayed/harness/per-phase booleans/reason/error, no transcript bodies) via generate.ts's leanContainerReplaySummary, matching packages/confirm/src/live.ts's own dast.probe audit convention of structural fields only.
Not Yet Wired to Production: FixGenerationContext.containerProof.targetRepoDir (a checkout of the full target application, required to build a real container) is not yet populated by apps/worker/src/runners.ts — the same documented not-yet-wired pattern as ConfirmInput.repoRoot for E1's investigation loop. Enabling containerProof without a directory just yields the vitest fallback; it is fully built, real-Docker tested (tests/fix.container-replay.test.ts), and exported, awaiting that wiring plus a real evidence source for targetRepoDir in a follow-up.

Fix Persistence
Fix Entity: Synthesized remediations are saved as Fix rows in Postgres via packages/state-store, storing the unified diff string, rationale, proofOfFixTest JSON object (including the optional E13 containerReplay evidence block when present), risk class, and risk rationale.

Constraints and Edge Cases
AGENT NOTE: Generated patches must be syntactically valid unified diffs. The module validates diff formatting before writing to the database.
AGENT AVOID: Never classify authentication, authorization, or crypto changes as auto-eligible, regardless of configuration settings.

Hardening Recommendations Are Explicitly Out of Scope (B9)
AGENT NOTE: Blue-team config and infrastructure hardening guidance — security headers, Content-Security-Policy, cookie policy, rate limits, WAF rules, network policy, and framework configuration — is generated by a genuinely separate package, packages/hardening, not by this module. That package never imports packages/fix and produces no diff, patch, or RiskClass field of any kind; every recommendation it generates is advisory-only and is never eligible for the auto-eligible/human-required classification described above or for automated pull request creation. This is a deliberate architectural boundary, not an oversight: code-fix auto-eligibility (this module) and config/infra hardening advice (packages/hardening) carry different safety guarantees and must never share a classification path. See docs/modules/reporting-vcs.md and packages/hardening's own module doc comment (packages/hardening/src/index.ts) for the full rationale. packages/hardening is not yet wired into Layer 5 report assembly.
